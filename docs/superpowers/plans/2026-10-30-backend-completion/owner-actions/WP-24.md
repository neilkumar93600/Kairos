# WP-24 owner actions: inbound mail route, encrypted bodies, Gmail confirmations

The code is on branch `wp/24`. The order below matters, because the migrations run while the previous release still serves. Sections 1 and 2 are needed before the new route takes mail. The rest follow it.

## 1. Before deploying

| Variable | Services | Value |
|---|---|---|
| `POSTMARK_INBOUND_PATH_SECRET` | api only | `openssl rand -hex 24`. At least 32 characters |
| `POSTMARK_INBOUND_BASIC_USER` | api only | Any short name, e.g. `postmark` |
| `POSTMARK_INBOUND_BASIC_PASSWORD` | api only | `openssl rand -hex 24`. At least 32 characters |
| `INBOUND_EMAIL_DOMAIN` | api, worker | **Your decision: the Postmark inbound domain.** The default is `replies.kairos.app`; the specs also say `reply`. Addresses already issued keep the domain they were issued with, so settle this before real users sign up |
| `INBOUND_PLAINTEXT_DUAL_WRITE` | api, worker | Leave unset (on) for now. See section 4 |

`DATA_KEKS` must already be set (WP-17). Until the secrets are set, the new route answers every call as a route that does not exist, and the old `?token=` route keeps working.

In Postmark, under the server's Inbound settings, turn on **Include raw email content in JSON payload**. Gmail confirmations are checked against the raw message.

**Do this before anyone sets up Gmail forwarding.** With it off, every real Gmail confirmation counts as unverifiable. It is stored hidden with no code, the user sees nothing, and the log says `mail claiming Google's forwarding sender has no valid DKIM signature` with `rawEmail: false`. The metric is `inbound.dropped{unverifiable_confirmation}`.

## 2. Move Postmark to the new route

Deploy, then set the server's inbound webhook URL to:

```
https://<BASIC_USER>:<BASIC_PASSWORD>@<api host>/api/webhooks/postmark/inbound/<PATH_SECRET>
```

Send one mail to a forwarding address and check that it appears in the inbox.

A wrong secret or password answers 404, exactly like a missing route, so nothing in Postmark tells you which part is wrong. Postmark retries a non-200 answer, so a mistyped URL costs retries rather than mail if you fix it within about 10 hours. Sentry's `inbound_token_rejected` signal fires on repeated rejections.

**Removing the legacy route** (`POST /api/webhooks/inbound-email`, `INBOUND_WEBHOOK_SECRET`) is a later change. Wait until all three hold:

- the new route has received a real message;
- the metric `inbound.legacy_calls` has been zero for 48 hours;
- 7 days have passed since the move.

**Rotating the secrets later:**

1. Put the old values in `POSTMARK_INBOUND_PATH_SECRET_PREVIOUS` and `POSTMARK_INBOUND_BASIC_PASSWORD_PREVIOUS`.
2. Set the new values and redeploy.
3. Update the URL in Postmark.
4. Clear the `_PREVIOUS` values after a day, when Postmark's retries are over.

In an incident, leave `_PREVIOUS` empty (docs/runbook/incident.md).

## 3. S-G1: the sample mail

Your input: one real Gmail forwarding confirmation.

In a test Gmail account, go to Settings > Forwarding > Add a forwarding address, and enter a Kairos forwarding address. Take the raw JSON from Postmark > Inbound > the message.

**Check that it worked:** `GET /api/forwarding/status` shows the code, and an email with the code reaches the account address.

Every template detail below is my reading of the specs and memory, not of a real mail, so the sample has to confirm them. If one is off, the confirmation is treated as forged or ordinary, and it needs a code change in `services/forwarding.ts`:

| Assumed | Where |
|---|---|
| The sender is exactly `forwarding-noreply@google.com` | `GMAIL_FORWARDING_SENDER` |
| The signature's `d=` is exactly `google.com`, and it signs From and To | `verifyDkim` |
| The To header names the forwarding address | `verifyDkim` |
| The subject is `(#<code>) Gmail Forwarding Confirmation ...`, or starts with `Gmail Forwarding Confirmation` | `CONFIRMATION_SUBJECT` |
| The body has `Confirmation code: <6 to 12 digits>` | `parseGmailForwardingConfirmation` |
| The link is on `mail-settings.google.com` | `FORWARDING_LINK_HOSTS`. The spec also lists Gmail's main web host. I left it out because `test/inv6-policy.test.ts` refuses that name in `src/`. If the sample uses it, that guard needs an exception |

Please send me the sample so it can become a test fixture. Today's DKIM tests sign their own messages.

## 4. Encrypting the old bodies, in this order

The migrations and the first deploy leave `text_body` readable, because the previous release reads only that column. Until step 3 below, a rollback is safe.

1. **Deploy this release.** Migrations 0018 and 0019 run first. New mail is written both encrypted and in clear.
2. **Encrypt the existing rows**, once the previous release's api and worker are gone:
   `railway run --service worker -- npx tsx scripts/backfill-inbound.ts`
   This also marks old classified rows and cuts over-long senders and subjects. It prints a JSON report, and `unencryptedLeft` must be 0. Plaintext stays. It is safe to run again.
3. **One release later**, when you will not roll back to a release older than this one, set `INBOUND_PLAINTEXT_DUAL_WRITE=0` on the api and worker and redeploy.
4. **Empty the plaintext:**
   `railway run --service worker -- npx tsx scripts/backfill-inbound.ts --null-plaintext`
   It refuses while the flag is on, and it never empties a row without ciphertext.
5. **Check:** `select count(*) from inbound_emails where text_body is not null;` must return 0. This is the WP-24 acceptance.
6. **WP-46** then validates `inbound_emails_sender_len_ck` and `inbound_emails_subject_len_ck`, adds the checks the old classify job would have broken (`link_reason`, `classified`, `offer_needs_rule`), and drops the column. Do not run that before step 5.

## 5. Decisions to confirm

| Item | What ships | Your call |
|---|---|---|
| **Rules changes, version 2** | The spec asks for an owner review of any rule change. The 256-case golden file found three bad results, and I narrowed the rules for each (next table). `RULES_VERSION` is now 2 | Please review `services/email-classifier.ts` |
| **Forged Google sender** | The spec says to treat a mail without a valid signature as ordinary mail. I hide it instead (stored as `spam`, no body, deleted at 30 days), because the inbox preview would otherwise show its link | Tell me if you prefer the spec's behaviour |
| Spam thresholds | Restrict at 5, hide at 8, as given. They are constants in `services/inbound.ts` and the spec calls them guesses | Re-check on the beta sample |
| `companies.domains` | The linker reads it, but nothing fills it yet (seed or admin edit, WP-23 and WP-27). Until then most domain links come from the ATS tier, and direct employer mail links by name or not at all | None now |

The three rule corrections:

| Wording | Was | Is now |
|---|---|---|
| "pleased to extend an offer for an interview", "a job interview" | offer | interview |
| "unable to extend you an offer", "cannot extend an offer" | offer | not an offer |
| "unfortunately we need to reschedule your interview" | rejection, which is final on the application | interview |

Known limits, pinned in the golden file so a change to them is deliberate:

- A bare "job offer" in any text still tags `offer`, for example a newsletter about job offer scams.
- A bare "unfortunately" still tags `rejection`, for example "the cafe is closed".
- If such a mail links to an application, it moves the stage, and `rejected` is final. The `linked_by` and `rule_kind` columns record how it happened.
