# WP-00 owner actions

Code for WP-00 is merged-ready on branch wp/00. These steps need your accounts and cannot be done by an agent. Do them in this order; items 1 to 3 are the urgent ones.

## 1. Set OWNER_USER_IDS on sd1-api (do this BEFORE deploying WP-00, or you lose the cloud channel)

The cloud channel is now owner-only and fails closed: with the variable unset, nobody can approve for the cloud applier, including you.

1. Find your user id: sign in to the staging web app, open `https://<your-api-host>/api/me` in the same browser (or run `select id from "user" where email = 'neilkumaroff@gmail.com';` in the Railway Postgres query tab). Copy the `user.id` value.
2. Railway > project > service `sd1-api` > Variables > New Variable: `OWNER_USER_IDS` = that id. Several ids go in one comma-separated value.
3. Redeploy `sd1-api`. Check: a non-owner account approving with channel `cloud` gets 403; yours succeeds.

The worker (`sd1-applier`) now enforces the same gate, so set `OWNER_USER_IDS` on `sd1-applier` too (same value). A non-owner's approved cloud row, whether approved before the gate or retried from the queue, is marked failed with "The cloud applier is not open yet" and costs no credit.

You can still check for already-approved cloud rows from other users that predate this change:

```sql
select id, user_id, status from applications
where channel = 'cloud' and status in ('approved', 'submitting') and user_id <> '<your user id>';
```

If any rows come back, the worker will fail them safely once deployed; moving them to `withdrawn` first just keeps the users' lists tidy.

## 1b. Deactivate boards pasted before WP-00

New pasted boards are stored inactive, but boards pasted before this change were stored active, so the poller still fetches them and scores every posting for every user. The `companies` table has no "source" column, so this cannot be done automatically. In the Railway Postgres query tab, list the active companies and untick the ones you did not curate yourself:

```sql
select c.id, c.name, c.ats, c.board_token, c.priority, c.careers_url, c.created_at,
       (select count(*) from jobs j where j.company_id = c.id) as postings
from companies c
where c.active
order by c.created_at desc;
```

Boards a user pasted usually have no `careers_url`, are not `priority`, and were created after your seed date. Deactivate them (put the ids you chose in the list):

```sql
update companies set active = false where id in ('<id1>', '<id2>');
```

Their jobs stay visible; they just stop being polled.

## 2. Spend limits (Anthropic Console and Railway)

1. Anthropic Console > Settings > Limits: set a monthly spend limit (suggest a figure you can afford to lose in one bad day, for example USD 50 during the closed beta) and an email alert at 50 percent.
2. Railway > Workspace > Usage (or project Settings > Usage): set a usage alert and a hard limit at a figure you choose.
3. Both alerts must go to an inbox you read daily.

## 3. Rotate INBOUND_WEBHOOK_SECRET (Postmark and Railway)

The old token travelled in a query string that was logged and was checkable by anyone with a large gzip body, so treat it as exposed.

1. Generate a new value of at least 32 random characters, for example `openssl rand -hex 24`.
2. Postmark > Servers > your inbound stream > Settings > Inbound webhook URL: replace `?token=<old>` with `?token=<new>`. Save.
3. Railway > `sd1-api` > Variables: set `INBOUND_WEBHOOK_SECRET` to the new value. Redeploy.
4. Send a test mail to a forwarding address. A wrong or missing token now answers 403; Postmark retries a failed delivery, so a short gap between steps 2 and 3 loses nothing.

Note: the server now refuses gzip-encoded inbound bodies (415). Postmark sends plain JSON, so nothing changes; if Postmark's inbound log ever shows 415s, tell me.

## 4. Delete the local dump.rdb

A Redis snapshot file named `server/dump.rdb` in your main checkout (E:\download\auto-career\server\dump.rdb) holds whatever queue data your local Redis had, which can include job payloads. It is git-ignored (`*.rdb`) and not tracked. Delete it: `del E:\download\auto-career\server\dump.rdb`, and stop the local Redis first if it is running so it does not rewrite the file.

## 5. After deploying: Stripe check (optional)

Any subscription that was already paused by an old offer email (`metadata.pausedBy = offer-email`) stays paused. In the Stripe dashboard, search subscriptions for that metadata and resume the ones that should be billing.
