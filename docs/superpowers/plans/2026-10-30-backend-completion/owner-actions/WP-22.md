# WP-22 owner actions: the durable seam (Postgres outbox)

Nothing here blocks the code being merged. Steps 1 and 2 belong to the deploy of this package; step 3 is what proves it.

## 1. Re-run the role script after the migration (required, at deploy)

Migration `0026_wp22_outbox` adds the `outbox` table. Its grants are in `ops/provision-roles.sql`, so run the script once after the migration, as for any new table (`owner-actions/WP-12.md`). Nothing breaks in between: from the moment 0026 applies, the migrator's default privileges give `kairos_api` and `kairos_worker` select, insert, update and delete on the new table, so approvals keep working. The re-run narrows that to the matrix (no delete for the api, no insert for the worker).

The worker's Postgres pool grows by one, for the drain: 33 per replica at the default concurrencies, not the 32 in `owner-actions/WP-45.md`. Check it against `max_connections` only if you are close.

## 2. Add two Sentry alerts (recommended)

Page on messages titled `signal: outbox_dead`, as in `owner-actions/WP-27.md`. Add `signal: outbox_lag` too if you want to hear of a Redis outage from this as well as from the health checks. What each means and what to do is in `docs/runbook/incident.md`.

## 3. Run the chaos test (required before the cloud channel opens beyond you)

GitHub > Actions > Chaos > Run workflow, on the default branch once this is merged. It starts its own Postgres and Redis, runs 1,000 scripted approvals with random kills and one Postgres restart, and uses a scripted browser, so no employer is contacted. It takes about 12 minutes and prints a JSON verdict; a failure exits non-zero and names the applications.

**It has never run.** The first run may find bugs in the harness as well as in the seam. To run it elsewhere, read the header of `ops/chaos/run.ts`: it must be a new database and a new Redis, never the ones a service uses, because its applier writes real ledger rows.
