# WP-50 owner actions: newsletter sign-ups

The code is on branch `wp/50`. It needs no new variable: emailed links use `WEB_ORIGIN`, and the worker, which renders the confirm email, also needs `USER_HASH_KEY` (owner-actions/WP-25.md section 2). Without that key on the worker the confirm email job fails and retries; sign-ups are still stored. Staging first, then production.

## 1. Migration and roles (5 minutes)

The migration is `0018_newsletter`. It landed first, so group E's migrations follow it (0019 to 0025). Renumber only before the migration has been applied to staging or production. The migrator (`server/src/db/migrator.ts`) matches applied migrations by the journal's `when`: an edited file under the same `when` is refused, and a regenerated file under a new `when` runs again and fails on the existing table. If it has been applied, add a new migration instead of editing this one. After it runs, run `ops/provision-roles.sql` again (owner-actions/WP-12.md): it grants `newsletter_subscribers` to the api and the worker.

## 2. Postmark: one-click headers under DKIM (10 minutes)

Every newsletter email carries `List-Unsubscribe: <https://<WEB_ORIGIN>/api/newsletter/unsubscribe?token=...>` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click`. RFC 8058 and Gmail's and Yahoo's sender rules need both headers covered by the DKIM signature. Sign up on staging with an address you read, open the confirm email's original source, and check that the `DKIM-Signature` for your domain lists `list-unsubscribe` and `list-unsubscribe-post` in its `h=` tag. If it does not, ask Postmark support to include them for the server.

That URL goes through the web's `/api` rewrite, so check it there too: `curl -i -X POST -d List-Unsubscribe=One-Click "<the header's URL>"` on staging answers `200 {"ok":true}`, not a redirect (RFC 8058 forbids one). That test unsubscribes the address you signed up with.

Run the staging test only after the marketing branch has landed. Emailed links open `/newsletter/confirm` and `/newsletter/unsubscribe`, and those web pages do not exist until then, so the API-only `curl` check can pass while the flow a person follows is broken. Click through both links in the email as well.

## 3. The newsletter issues (decision, before the first one)

WP-50 takes sign-ups and sends the confirm email only. Nothing sends an issue yet. When something does:

- Send to rows with `status = 'confirmed'` only, on the **broadcast** stream.
- Give every email the headers of `newsletterHeaders(id)` and a visible unsubscribe link from `newsletterUnsubscribeUrl(id)` (`server/src/services/newsletter.ts`), a web page with a button. That link is the same for every email to one address and keeps working while the row exists.
- In Postmark, set the broadcast stream's unsubscribe handling to **None**, so Postmark does not add a second, unsynchronised unsubscribe link.
- Put the sender's postal address in every issue (CAN-SPAM; the same open item as WP-35).
- Prefer an unsubscribe token with an expiry. Today's token never expires while the row exists, and RFC 8058 puts it in the query string of the header URL, so Vercel and Railway request logs can hold it (the api's own logs do not). The blast radius of a leaked token is one unsubscribe, which is accepted for the confirm email.
- There are two lists. WP-35 (branch `wp/35`, in progress) builds account-level opt-out with `mail_opt_out`, so an account holder can opt out and still be a confirmed newsletter subscriber. The sender must go through the WP-44 notify core and check `email_suppressions` and `mail_opt_out` as well as subscriber status. Nothing sends issues yet, so nothing breaks today.
- Decide what an account opt-out means for the newsletter. On `wp/35` today, `mail_opt_out` holds only `digest`, `outcome_report`, `autopilot_summary` and `reminders`, with no newsletter key, and its send check takes a user id, which a subscriber row does not have. So the sender needs a rule for which keys stop an issue, and a way to find the account from the address (WP-35's `mail_opt_outs` table is keyed by address hash).

## 4. Privacy notice and counsel (decision)

Add to the privacy notice (owner-actions/WP-25.md section 4):

| Item | Default in code | Question for counsel |
|---|---|---|
| What a sign-up stores | The address, which form it came from, when it was asked for, confirmed and unsubscribed. No IP address or user agent. | Is the double opt-in record (confirmed_at and the form) enough proof of consent, or must the request's IP be kept too? |
| Unconfirmed sign-ups | Deleted 30 days after the last confirm email was asked for | Override with `RETENTION_DAYS=newsletter_inactive=<days>` on the worker |
| Unsubscribed sign-ups | Deleted 30 days after the unsubscribe | Same rule |
| Confirmed sign-ups | Kept until unsubscribe or an account erasure for the same address | Is a re-permission or inactivity purge required (for example after 2 years without opening)? We track no opens, so this would be by date |
| Mail to an address that unsubscribed | No list of unsubscribed addresses is kept. Anyone who types the address can trigger a new confirm email: at once while the row exists, and also after the row is deleted at 30 days. At most 5 sign-ups a day per address go through, and the person is not subscribed unless they confirm | Is that acceptable, or must an unsubscribe also block new confirm emails (a kept hash, as `email_suppressions` does)? |
| Spam complaints | An address with a spam complaint gets no confirm email, even if the person really is signing up: the form answers the same 202. Lifting a complaint: `docs/runbook/incident.md` | None |
| Erasure | An account erasure deletes sign-ups under the account's address and its aliases (`+tag`, Gmail dots). A person without an account who asks for erasure: delete by address by hand, `delete from newsletter_subscribers where email = lower('<address>')` | None |
