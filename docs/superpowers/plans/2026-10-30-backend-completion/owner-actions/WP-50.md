# WP-50 owner actions: newsletter sign-ups

The code is on branch `wp/50`. It needs no new variable: the api uses `WEB_ORIGIN`, and the worker, which renders the confirm email, uses `API_PUBLIC_ORIGIN` (owner-actions/WP-44.md section 3) and `USER_HASH_KEY` (owner-actions/WP-25.md section 2). Without those two on the worker the confirm email job fails and retries; sign-ups are still stored. Staging first, then production.

## 1. Migration and roles (5 minutes)

The migration is `0016_newsletter` on this branch. `backend/complete` has since taken 0016 and 0017 from WP-17, so the integration merge regenerates it as `0018_newsletter` (drizzle-kit, header kept). After it runs, run `ops/provision-roles.sql` again (owner-actions/WP-12.md): it grants `newsletter_subscribers` to the api and the worker.

## 2. Postmark: one-click headers under DKIM (10 minutes)

Every newsletter email carries `List-Unsubscribe: <https://<API_PUBLIC_ORIGIN>/api/newsletter/unsubscribe?token=...>` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click`. RFC 8058 and Gmail's and Yahoo's sender rules need both headers covered by the DKIM signature. Sign up on staging with an address you read, open the confirm email's original source, and check that the `DKIM-Signature` for your domain lists `list-unsubscribe` and `list-unsubscribe-post` in its `h=` tag. If it does not, ask Postmark support to include them for the server.

## 3. The newsletter issues (decision, before the first one)

WP-50 takes sign-ups and sends the confirm email only. Nothing sends an issue yet. When something does:

- Send to rows with `status = 'confirmed'` only, on the **broadcast** stream.
- Give every email the headers of `newsletterHeaders(id)` and a visible unsubscribe link from `newsletterUnsubscribeUrl(id)` (`server/src/services/newsletter.ts`). That link is the same for every email to one address and keeps working while the row exists.
- In Postmark, set the broadcast stream's unsubscribe handling to **None**, so Postmark does not add a second, unsynchronised unsubscribe link.
- Put the sender's postal address in every issue (CAN-SPAM; the same open item as WP-35).

## 4. Privacy notice and counsel (decision)

Add to the privacy notice (owner-actions/WP-25.md section 4):

| Item | Default in code | Question for counsel |
|---|---|---|
| What a sign-up stores | The address, which form it came from, when it was asked for, confirmed and unsubscribed. No IP address or user agent. | Is the double opt-in record (confirmed_at and the form) enough proof of consent, or must the request's IP be kept too? |
| Unconfirmed sign-ups | Deleted 30 days after the last confirm email was asked for | Override with `RETENTION_DAYS=newsletter_inactive=<days>` on the worker |
| Unsubscribed sign-ups | Deleted 30 days after the unsubscribe | Same rule |
| Confirmed sign-ups | Kept until unsubscribe or an account erasure for the same address | Is a re-permission or inactivity purge required (for example after 2 years without opening)? We track no opens, so this would be by date |
| Erasure | An account erasure deletes sign-ups under the account's address and its aliases (`+tag`, Gmail dots). A person without an account who asks for erasure: delete by address by hand, `delete from newsletter_subscribers where email = lower('<address>')` | None |

## 5. Known limit: a link scanner can confirm (decision)

The contract makes `GET /api/newsletter/confirm` act directly. A mail scanner that opens every link (some corporate gateways do) confirms the subscription without the person, which weakens the double opt-in as evidence of consent. A `HEAD` changes nothing, but a scanner's `GET` does. If counsel or a complaint makes this matter, the fix is a confirm page on the web that posts the token back (a contract change for FE-pages and this package, about half a day).
