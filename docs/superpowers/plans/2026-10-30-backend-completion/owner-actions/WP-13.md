# WP-13 owner actions: Postgres 18, PITR, encrypted backups, the money journal and the restore drill

The code is on branch `wp/13`. What it adds:

- **The money journal.** Every minute the worker copies the new `credit_ledger` rows, application status changes and processed Stripe event ids (ids, enums and times, no text) to R2 `kairos-backups/journal/`. An hourly `journal-reconcile` merges late commits and fills gaps. After a restore to an older point, `scripts/journal-replay.ts` puts the ledger back and closes every application the restore re-opened, so nothing is sent twice.
- **Encrypted dumps.** A new Railway cron service, `pgbackup` (`ops/pgbackup/Dockerfile`), writes a core dump nightly and a full dump on Sundays, encrypted with `age` to two public keys, with a manifest of row counts and checksums. The worker checks hourly that both are fresh.
- **The restore tools.** `scripts/backup.ts restore` decrypts a dump on your machine, restores it into a scratch database and compares every row count with the manifest. Runbooks [R-DR-1](../../../../runbook/R-DR-1.md) (PITR) and [R-DR-2](../../../../runbook/R-DR-2.md) (dump plus journal, and the monthly drill).
- **Parameters.** `ops/pg-settings.sql` sets the 06-infrastructure 1.7 server parameters; `ops/provision-roles.sql` gains a 5-second `lock_timeout` for the api, worker and applier roles.

Deploying `wp/13` is safe before any step below. Until the worker holds the backups token (owner-actions/WP-14.md step 4), the journal and the backup check do nothing. Once it does, the journal starts writing at once, and the hourly backup check raises `backup_stale` until step 6 has produced the first dumps. Do steps 1 to 6 on staging first, then production.

The acceptance of WP-13 is yours to run: steps 2, 7 and 8 below. Everything else gets you there.

## 1. Decide: PITR (decision)

Railway's PITR archives every WAL segment with pgBackRest: a restore to any second of the last about 4 weeks, RPO about 2 minutes (06-infrastructure 5.1, 5.2). Without it, the newest restore point is last night's dump, and only the ledger and sends come back to the minute through the journal.

## What this package does not cover, and where it differs from the specs

- **One journal object per minute of commit time**, not one per run (`<hhmm>-<executor>`): re-running a minute writes the same object, and a minute written 15 seconds after it closes keeps the worst case near 1 minute 15 seconds. The cursor is `journal/cursor.json` in R2. There are no `attempt` lines: `submission_attempts` does not exist yet (WP-29/WP-42 add them).
- **Replay closes applications itself** instead of listing them for a manual `needs_check` (a status that does not exist). It only moves along the database's own status guard into `submitting`, `submitted`, `failed` or `withdrawn`, never into `approved` or `draft`, and lists every other difference.
- **Stripe events are listed for resending, not inserted**, because their effect on subscriptions is not journaled.
- **Tombstone replay** (06-infrastructure 5.6 step 7) waits for WP-25; the runbooks say how to check deletions by hand until then.
- **No archive-lag alert yet** (ops-62, `ops_archive_status()`). Whether Railway's PITR image fills `pg_stat_archiver`, and how an idle database's lag reads, is part of S-P1 (step 2). Send me `select * from pg_stat_archiver;` with the step 2 output and I add it to the hourly backup check.
- **Dumps use pg_dump's default compression**, not `zstd`, so any pg_restore 18 reads them. **A dump is one R2 upload**, at most 5 GiB; the manifest warns from 4 GiB (`backup_warning`), long before beta sizes get there.
- **Only the applier refuses `DATABASE_BACKUP_URL` at boot**; keep it off the api and worker by step 6's "this service only", as with the backups token in WP-14.
- **R-DR-3** (restore into another region or project) is not written; R-DR-2 with a new project is its core.
- **pg_trgm** is not created by a migration here: nothing uses it yet.
