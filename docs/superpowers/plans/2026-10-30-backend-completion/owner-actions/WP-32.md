# WP-32 owner actions: Stripe store-then-process and credit balances

Nothing here blocks merging the code. Step 1 belongs to its deploy. Steps 3 and 4 are the two acceptance criteria that only real Stripe test mode can prove: the build has no Stripe key, and no test calls Stripe.

## 1. Deploy (required)

1. Let the migration run, as for any release (`0029_wp32_billing`; the number may move again at merge). It locks `credit_ledger` and `applications` against writes for the moment it takes to compute every user's balance: well under a second at beta size. A send or approval in that moment waits, or fails after 5 s and is retried.
2. Deploy api and worker together if you can. Either order is safe: a new api with an old worker stores events that wait until the new worker arrives; an old api with a new worker processes events inline as before.
3. Run `ops/provision-roles.sql` again (`owner-actions/WP-12.md`). Until then the runtime roles hold the default privileges on the new table, which is enough for the code; the script narrows them to what the release needs (no write on `credit_balances`, EXECUTE on `ensure_credit_balance`, and INSERT on `outbox` for the worker).
4. After the worker is up, check nothing is waiting: `select status, count(*) from stripe_events group by 1` shows no `received` row older than a few minutes.

Do not roll the api back to the previous release once events have been stored by this one: the previous release never processes a `received` row. If you must, roll the worker forward again as soon as you can, and the daily reconcile grants whatever was paid meanwhile.

## 3. 14 clean days on a test clock (required for the acceptance; never run)

On staging, with its Stripe key in test mode (`sk_test_...`), the test-mode webhook pointed at staging, and `STRIPE_PRICES` holding the nine test-mode prices:

```
npx tsx scripts/stripe-test-clock.ts setup --tag beta1       # prints the clock id and one customer per price
npx tsx scripts/stripe-test-clock.ts run --clock <clock id> --days 14
```

Run it with a `DATABASE_URL` that may insert `"user"` (the api's role or the owner). `run` advances the clock one day at a time, waits for the webhooks to land and the queue to drain, and runs the invariant checks and the reconcile. It prints one line per day and exits 1 at the first finding. Fourteen clean lines, exit 0, is the proof. Each simulated day can take a few minutes, so the whole run takes about an hour. The script refuses a live key and `NODE_ENV=production`. It has never run, so its first run may find bugs in the script as well as in the code.

## 4. A recorded replay (required for the acceptance as written)

After step 3, record one customer's real events:

```
npx tsx scripts/stripe-test-clock.ts record --clock <clock id> --user clock-beta1-pro-month --name pro-month
```

This writes `server/test/fixtures/stripe/recorded/pro-month.json`. `test/stripe-replay.int.test.ts` replays every file there twice and requires identical ledgers and one grant per paid invoice. Until a file exists, that test is skipped and only the hand-built fixture runs. The recording holds Stripe's raw test-mode events, so the customer name is "Test Clock" and the address `@example.com`. Look at it before you commit it.
