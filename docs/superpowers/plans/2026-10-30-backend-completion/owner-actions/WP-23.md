# WP-23 owner actions: matching interim

The code is on branch `wp/23`. What changes when it deploys:

- **Imported boards.** A board a user pasted is polled only to close the jobs already stored. It inserts nothing and costs no scoring call until you activate it at `POST /api/admin/companies/:id/activate`. Activating starts normal polling and scoring: a large board's whole listing is inserted and scored, within the daily caps.
- **Polling.** Polls are safer and quieter: ETag and 304, a rest for a host that answers 429 or 403, no mass close on a truncated listing, and two 404s before a board is switched off. Lever EU boards now work.
- **Scoring.** One SQL query per new posting decides who could want it. Pairs under the F1 floor cost no call. Scores under a user's bar are kept, so they are not paid for twice.
- **New queue.** Links Kairos cannot read collect at `GET /api/admin/board-requests`, as host and path only.

Deploying is safe before steps 1 and 2 below. Until then the conservative caps apply, and nothing polls that was not polling already.

## 1. Pin the per-plan scoring caps

`shared/src/plans.ts` holds `dailyScoringCap` per plan: Free 20, Starter 120, Pro 140, Max 350.

The env variable `MATCHING_DAILY_CAP_MAX` (api and worker) sits on top of those numbers, and every plan is held to the lower of the two. **The default is 140, so Max runs at 140, not 350, until you decide.**

Decide:

1. Are the four plan numbers right? If not, tell the team the numbers, or change them in `plans.ts`.
2. Then set `MATCHING_DAILY_CAP_MAX` high enough for them (for example `350`) on both the api and the worker.

**The raise is yours to make and stays explicit.** Max equals Pro's 140 until you raise the variable.

It also works as a brake. Lowering it cuts every plan at the next deploy or restart, and `0` stops pipeline scoring. For an immediate stop with no restart, use the `pause_scoring` flag.

**Pinning the scorer to Sonnet silently cuts scoring volume.** `model_pin:fit-scorer` to Sonnet costs about 20x per call. The per-user spend cap (`dailyModelSpendCapUsd`) then stops a user after about a twentieth of the calls, with no error and no signal: pairs past it are simply not scored that day. Treat a pin on this agent as a short rollback, not a setting.

The cost ceiling, at the spec's expected $0.00021 per call, is about `users x cap x $0.00021` a day. At 10,000 users on Pro's 140 that is about $294 a day if every user hit the cap. Real use should be far lower, but that is the worst case to check against your Anthropic spend limit.

## 2. Provide the company seed list (about 2,000 boards)

Nothing supplies the list today, and a fresh database has nothing to poll until it is loaded. Provide a JSON array:

```json
[
  { "ats": "greenhouse", "boardToken": "stripe", "name": "Stripe", "domains": ["stripe.com"], "careersUrl": "https://stripe.com/jobs" },
  { "ats": "lever", "boardToken": "acme", "name": "Acme", "region": "eu" }
]
```

`ats`, `boardToken` and `name` are required. `region` is for Lever only (`us` by default). `domains` is what lets a pasted `?gh_jid=` link on that employer's own site resolve to this board.

From `server/`, with `DATABASE_URL` and `REDIS_URL` in `.env` (the second only because the env check requires it; the script does not use Redis):

```
npm run db:seed -- path/to/companies.json
```

- The file is validated first. Any problem is listed with its row number and nothing is written.
- It is safe to rerun. Names, domains, careers URLs, priority and region are refreshed.
- **A board on your list that was waiting as an import becomes active.** Being on your list counts as activating it, and each one writes an `ops_audit` row (`company_activate`, actor `system:seed`).
- The whole file is one transaction: a failure writes nothing.
- A company you stopped, or one that 404'd, stays inactive.
- First polls spread over 30 minutes.

**Seeding starts spend.** Each seeded board's postings fan out to scoring on its first poll, within the caps. Consider loading a small batch first and watching `llm_calls` and the spend page.

## 3. Work the review queue, when you have time

`GET /api/admin/board-requests` lists open requests, most recent first. To add one, put the board in your seed file and rerun step 2.

**Nothing resolves an open request yet.** Adding the board does not mark its request, and no route does. Close one by SQL, or leave it: rows expire 180 days after the last sighting.

```sql
update board_requests set status = 'rejected', resolved_at = now() where id = '<id>';
```

## Pausing scoring: what happens to the work

The flags hold scoring in the same way but differ on new work:

| | `llm_paused`, `agent_disabled:fit-scorer` | `pause_scoring` |
|---|---|---|
| Model calls for scoring | Stopped | Stopped |
| Pairs already queued | Kept | Kept |
| A posting that arrives during it | Queued, scored when it lifts | **Not scored** when it lifts |
| A backfill asked for during it | Queued, scored when it lifts | **Skipped** |

- **Pairs resume by themselves.** A lane holds its members and looks again every 15 minutes, so what is queued is scoring within about 15 minutes of lifting the flag. Held pairs take no scoring slot and cost nothing.
- **Queues grow during `llm_paused` and `agent_disabled`.** Use `pause_scoring` for a stop of days: every lane keeps growing in Redis, which refuses writes when full.
- **What a long pause queues can exceed a day's cap.** When it lifts, pairs past a user's daily cap are not scored, as on any day.
- **Lanes expire 7 days after the last posting added.** After a pause that long, what was queued is gone.
- **After `pause_scoring`:** skipped postings wait for WP-34's nightly re-score, and until WP-34 ships only a user's own backfill picks them up. A skipped backfill runs again on the user's next preference save or first confirmed fact.
- **An import during any of the three succeeds, unscored.** The next import of that posting scores it.

## 4. Before deploying: count the rows

Migration `wp23_import_backfill` updates `matches` in place, which the design allows while the table is under 100,000 rows:

```sql
select count(*) from matches;
```

It moves old gate-failed imports from `skipped` to `below_bar`. A user's own skip of such an import cannot be told apart from the system's and moves too. Neither status shows in the feed, and "Tailor anyway" still queues both.

## Roles and retention

- Run `ops/provision-roles.sql` again after the migration: `board_requests` needs its grants (api select, insert, update; worker select, delete).
- `board_requests` is registered in the privacy registry: exported with the account and erased by cascade. Its retention is 180 days, overridable through `RETENTION_DAYS` as `board_requests=<days>`. This period is the builder's default, because the spec names none. Confirm it with counsel alongside the WP-25 periods.
