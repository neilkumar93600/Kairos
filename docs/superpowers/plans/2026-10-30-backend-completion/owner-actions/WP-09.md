# WP-09 owner actions: scheduled maintenance and reconcilers

The code is on branch `wp/09`. No new environment variable, service or migration. At boot the worker registers its job schedulers in Redis (`server/src/jobs/schedules.ts`); one run per tick happens across all worker replicas.

| Schedule | Cadence | What it does |
|---|---|---|
| `llm-partitions` | daily 03:00 UTC | `llm_calls` partitions for the current week and six more; alert if `llm_calls_default` holds a row; drop weeks older than 90 days once rolled up |
| `sweep-submitting` | every 30 s | A cloud send stuck in `submitting` over 10 minutes becomes failed and unconfirmed; never resent, no credit used |
| `reconcile-apply` | every minute | An approved cloud application with no queued job gets it back |
| `redrive-drafts`, `redrive-inbox` | every 5 minutes | A draft never tailored, or a reply never classified, whose job was lost gets it back |
| `bootstrap-users` | every minute | A user whose sign-up hook failed gets the profile, the free plan and the free grant, once |
| `auth-sweep` | daily 03:30 UTC | Deletes accounts unverified for 14 days, sessions 7 days past expiry, codes 1 day past expiry |

## 1. Deploy before 2026-12-06, or extend the partitions by hand now

The `llm_calls` partitions that migration 0002 created run out on about **2026-12-07**. After that, every model call's ledger row lands in `llm_calls_default`. The first 03:00 UTC run after `wp/09` deploys fixes it. If that deploy might come later, run this once as the database owner today. It is idempotent and adds about two weeks:

```sql
select llm_calls_ensure_partitions(6);
```

## 2. Sentry alert rules

In project `kairos-server`, add these beside the rules of owner-actions/WP-11.md step 5. Use the same triggers: a new issue, a regression, or more than 5 events in 1 hour.

| Rule | Condition | Action |
|---|---|---|
| Maintenance, page | tag `signal` equals `llm_calls_default_rows` | Page |
| Maintenance, email | tag `signal` equals `submitting_swept` or `signup_repaired` | Email |

What each signal means, and what to do about it, is in `docs/runbook/incident.md` ("Security signals"). A failed maintenance job is an ordinary Sentry error on queue `maintenance`, and the existing "New error" rule covers it.

## 3. One-time check (about 5 minutes, the day after the deploy)

Run as the owner on production:

```sql
-- Weekly partitions with no week missing; the last one is six ISO weeks after the current week.
select c.relname from pg_inherits i join pg_class c on c.oid = i.inhrelid
 where i.inhparent = 'public.llm_calls'::regclass order by 1;
-- Must be 0.
select count(*) from llm_calls_default;
-- Must be 0 rows: no cloud send left in submitting.
select id from applications where status = 'submitting' and updated_at < now() - interval '11 minutes';
```

Reply "WP-09 checked" with the last partition name.
