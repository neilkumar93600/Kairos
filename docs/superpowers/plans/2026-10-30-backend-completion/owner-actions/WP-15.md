# WP-15 owner actions: Railway infrastructure as code and a production environment

The code is on branch `wp/15`. **Deadline: 2026-12-01.** On that date Railway stops reading `railway.json`, which is where the staging services get their pre-deploy migration, healthchecks, restart policy and drains today. Two Railway sources say so:

- https://docs.railway.com/infrastructure-as-code: "Existing Config as Code files stop being read on **2026-12-01** (hard cutoff)." The Config as Code page has the same date in a warning banner, and adds "New services cannot opt into Config as Code."
- https://railway.com/changelog/2026-08-20-railway-anon (2026-08-20): "Config as Code is going away in favor of our new IaC SDK. Starting August 28, services in new projects will no longer be deployed using Config as Code (new services in existing projects should be fine), with the old system going away on December 1."

Put both quotes in the pull request description.

What changed:

- `.railway/railway.ts` declares the whole Railway project, `kairos`: Postgres, Redis, `api`, `worker` and `applier`.
  - Healthchecks on all three services, restart `ALWAYS`, drains of 60/60/180 s and a 20 s overlap on the api.
  - The migration runs before each api deploy.
  - Replicas: 2/3/6 in production and 1 each in staging.
  - CPU and memory limits, and Node heaps of 768/1536/1024 MB.
  - The branches: staging deploys `main` after its GitHub checks pass, and production deploys `release`.
  - The variables each service may hold. Secret values are never in the file: you set them by hand, sealed (step 4).
- `ops/railway-limits.json` records the sizes. A test keeps it, the file, the shutdown deadlines in the code and the secret rules in agreement.
- `server/railway/*.json` are deleted. Railway refuses to plan a service that a config file still manages.
- `railway-config.yml`:
  - A pull request that changes `.railway/` gets the staging plan as a comment, and merging applies exactly that plan to staging.
  - Every night it fails, and GitHub emails you, if staging or production differs from the file.
- `staging-gate.yml` runs after each staging deploy:
  - health through the web;
  - `scripts/smoke.mjs` through the web (sign up, verify the emailed code, sign in, `/api/me`, delete the user);
  - the contract suite.
- `promote.yml` is the only way to production. It refuses a commit that is not on `main` or has no green CI and staging gate. It applies that commit's `.railway/railway.ts` to production, then moves `release` to the commit.

Order matters. Do steps 1 to 4 from the branch, **before merging**, so the new staging exists when `main` loses the JSON files. Then do steps 5 to 8. Finish by 2026-12-01; the old `sd1` services lose their config that day either way.

## 3. First apply, staging first (from the branch, about 20 minutes each)

From the repository root on `wp/15`, with the Railway CLI 5.71.0 or later:

```bash
npm ci --ignore-scripts
railway login
railway link            # project kairos, environment staging
railway config plan
```

The plan should show only creations: `database.Postgres`, `database.Redis`, `service.api`, `service.worker`, `service.applier`. Check the region `us-east4-eqdc4a` and the replicas and limits in the details (`railway config plan --verbose`). Then run `railway config apply`.

The services start deploying and fail until they have variables. That is expected. Then:

1. `api` > Settings > Networking > Generate Domain, target port `4000`. This is the staging API origin.
2. Postgres: run `ops/provision-roles.sql` as in owner-actions/WP-12.md step 5.2. It creates `kairos_migrator`, `kairos_api`, `kairos_worker` and the rest, with new passwords for this database. Add `-v applier_password=...` here too, because this database has no applier role yet. If you turn on Railway's connection pooling, the runtime URLs go through it and the migrator URL does not.
3. Set the variables of step 4 and redeploy `api`. Its first pre-deploy creates every table as `kairos_migrator`. Run `ops/provision-roles.sql` once more, with no passwords, to grant the runtime roles on the new tables (WP-12 step 5.2). Then redeploy `worker` and `applier`. All three should go `Active` with their healthchecks passing.
4. Run `railway config plan` again. It must say "Your Railway configuration is already up to date."

Then repeat the whole step with `railway link` to environment **production**. Use production values in step 4: live Stripe, the production Postmark server, the `kairos-prod-*` Anthropic keys and the R2 buckets without the `-staging` suffix (owner-actions/WP-14.md).

If the first plan refuses `preserve()` for a variable that does not exist yet, create the three services by hand first: + New > Empty Service, named `api`, `worker` and `applier`. Set their variables (step 4), then plan again; the apply adopts them by name.

Notes:

- **Both `api` and `worker` need the `BETTER_AUTH_*`, `WEB_ORIGIN` and `INBOUND_WEBHOOK_SECRET` values.** They share one env schema, and the worker refuses to boot without them. 06-infrastructure 4.4 wants the worker without them; that needs a schema split, which is not in this package.
- **`OWNER_USER_IDS` waits for your account.** The new databases are empty: sign up on each environment first, read your id from `/api/me`, set it, and redeploy.
- **Staging `HEARTBEAT_URL`s:** use monitors that only email, not page.
- **Sealed values are invisible to the CLI.** `railway run` and `railway variables` do not see them. A script that needs one (such as `r2:smoke`) takes the value from your password manager.
- **A variable set by hand that the file does not list is drift.** The next plan shows it as a deletion. The apply jobs never delete, so they stop, and the nightly job fails. In an incident, setting a kill switch by hand is fine (`PAUSE_SCORING`, `LLM_SHED_LEVEL`, `CLOUD_APPLIER_OPEN`). Within a day, either add it to `.railway/railway.ts` in a pull request or remove it (06-infrastructure 2.5).

## What this package does not cover, and where it differs from the specs

- **Production gets its config from `promote.yml`, not on merge.** 06-infrastructure 1.8 applies the file to both environments on merge. Here a merge applies it to staging only, and production gets the file of the commit being released. Config and code then reach production together, and the production token never meets a pull request. The production plan appears in the promotion's run summary rather than on the pull request.
- **Secrets are sealed per-service variables kept with `preserve()`**, as 06-infrastructure 1.8 says. They are not shared variables, and constants the code owns are literals in the file.
- **The CLI is a pinned binary, not the `railwayapp/config` action.** The action installs the repository with npm install scripts on and uses actions by tag (06-infrastructure 3.10), so the workflows install the Railway CLI from its release tarball, pinned by version and SHA-256.
- **The staging gate** is health, the sign-in smoke and the contract suite (against the QA mock until the resume suite routes exist, WP-17). Still to come: the full journey (upload, draft, approve, cloud apply against the fake ATS: `ops/fake-ats`, WP-28), the k6 load smoke (WP-28), queue chaos, the invariant queries (WP-27), and the contract replay against staging.
- **Promotion is still missing:**
  - the named Railway backup before a migration (WP-13);
  - the `bundle.sha256` proof;
  - service ordering (expand-only migrations make the order safe, 06-infrastructure 3.4);
  - post-deploy verification and automatic rollback. The WP-11 uptime checks page instead, and R-DEPLOY-1 now rolls back by promoting the last good SHA.
- **Preview environments (`pr-<n>`) are not set up.** The file refuses any environment other than `production` and `staging`.
- **New Railway resources must be added to `.railway/railway.ts`.** That includes `pgbackup` (WP-13), `grafana` (WP-27) and connection pooling if it shows up as a service. Anything created by hand appears as a deletion in the next plan.
- **Not set:** custom domains (the api uses the generated domain; `api.<domain>` is one line), `NODE_OPTIONS=--dns-result-order=ipv6first` (only needed on an IPv6-only private network, 06-infrastructure 1.4) and the applier's concurrency (WP-45).
