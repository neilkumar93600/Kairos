# WP-12 owner actions: database foundations

The code is on branch `wp/12`. These steps need Railway and the database superuser, so only the owner can do them. Do steps 1 to 3 before deploying `wp/12` to sd1, step 4 to deploy, then step 5 (the role cutover) when you have half an hour to watch the logs. Nothing changes for users until step 5, and step 5 is reversible per service.

What changed for you:

- The server talks to Postgres through `pg` 8.23.1 instead of postgres.js. Every query is unnamed, so nothing prepared outlives a transaction: the services are safe behind PgBouncer in transaction mode.
- `node dist/migrate.js` (the api's pre-deploy command) is now our own runner. It takes advisory lock `7281551`, so two deploys never migrate at once; it commits per file; it retries a statement that waits more than 5 seconds for a lock (3 times, 10 seconds apart); and it refuses to run if a migration that already ran on the database was edited since. It connects to `DATABASE_UNPOOLED_URL`, or to `DATABASE_URL` while that one is unset. It keeps drizzle's `drizzle.__drizzle_migrations` table, so sd1 carries on where it is.
- Three migrations: `0005_fk_indexes` (indexes, built concurrently), `0006_backstops` (append-only ledger, status guard, fact guard, named checks) and `0007_profiles` (the full profiles column set and its guards).
- `ops/provision-roles.sql` now creates every role, not just `kairos_applier`.
- A production applier with `DATABASE_UNPOOLED_URL` set refuses to boot, as it does for the other secrets.

## 1. Confirm the Postgres version

Railway > Postgres service > Data (or `railway connect Postgres`), then run `select version();`. Record the answer in the WP-13 notes. The WP-12 SQL is Postgres 17-compatible on purpose (no `uuidv7()`), so it runs on either; 18 is what WP-13 (PITR, backups) is waiting for.

## 2. Confirm which URL each service uses, and whether PgBouncer is in front

Railway > each of `sd1-api`, `sd1-worker`, `sd1-applier` > Variables > `DATABASE_URL`. Note the host of each:

| Host in the URL | Meaning |
|---|---|
| `postgres.railway.internal:5432` (or the Postgres service's name) | Direct to Postgres |
| A PgBouncer service's internal host | Pooled. Open that PgBouncer service's Variables and note `POOL_MODE` (or `PGBOUNCER_POOL_MODE`): `transaction` or `session` |

Record both in the WP-12 acceptance notes. The code works either way. The one rule: `DATABASE_UNPOOLED_URL` (step 5) must point straight at Postgres, never at PgBouncer, because the migration lock and `SET lock_timeout` belong to one session.

## 3. Pre-check the data the new checks will guard (before deploying)

Migration 0006 and 0007 add checks that hold every new write. Over the rows already there they are `NOT VALID`, so the deploy cannot fail on old data, but an old row that breaks a check makes the next update of that row fail. Run this on sd1 as the superuser; every count should be 0:

```sql
select 'one free grant per user' as rule, count(*) from (
  select user_id from credit_ledger where reason = 'free_grant' group by 1 having count(*) > 1) d
union all select 'credit_ledger_sign_ck', count(*) from credit_ledger
  where ((reason in ('plan_grant','free_grant','refund_failed_submit') and delta > 0) or (reason = 'submission' and delta = -1)
     or (reason = 'expiry' and delta < 0) or (reason = 'admin_adjustment' and delta <> 0 and note is not null)) is false
union all select 'credit_ledger_shape_ck', count(*) from credit_ledger
  where ((reason in ('plan_grant','expiry') and stripe_invoice_id is not null and application_id is null)
     or (reason = 'free_grant' and stripe_invoice_id is null and application_id is null)
     or (reason in ('submission','refund_failed_submit') and stripe_invoice_id is null)
     or (reason = 'admin_adjustment' and stripe_invoice_id is null)) is false
union all select 'credit_ledger_note_ck', count(*) from credit_ledger where (note is null or note ~ '^[A-Za-z0-9 _:=.,/#-]{1,200}$') is false
union all select 'subscriptions_status_ck', count(*) from subscriptions
  where status not in ('active','trialing','past_due','unpaid','canceled','incomplete','incomplete_expired','paused')
union all select 'subscriptions_past_due_ck', count(*) from subscriptions where (status = 'past_due') <> (past_due_since is not null)
union all select 'jobs_source_ck', count(*) from jobs where source not in ('board','manual_url')
union all select 'contact_messages_topic_ck', count(*) from contact_messages where topic not in ('support','billing','partnership','press','other')
union all select 'profiles_onboarding_step_ck', count(*) from profiles where onboarding_step not in ('resume','confirm-facts','done')
union all select 'profiles_forwarding_address_ck', count(*) from profiles
  where (forwarding_address = lower(forwarding_address) and forwarding_address ~ '^[a-z0-9._+-]+@[a-z0-9.-]+\.[a-z]{2,}$') is false
union all select 'profiles_lengths_ck', count(*) from profiles
  where (char_length(phone) <= 40 and char_length(city) <= 120 and char_length(country) <= 120) is false
union all select 'profiles_urls_ck', count(*) from profiles
  where (linkedin_url ~* '^https?://[^[:space:]]+$' and char_length(linkedin_url) <= 300
     and github_url ~* '^https?://[^[:space:]]+$' and char_length(github_url) <= 300
     and portfolio_url ~* '^https?://[^[:space:]]+$' and char_length(portfolio_url) <= 300) is false
union all select 'applications_approval_shape_ck', count(*) from applications
  where ((status in ('approved','submitting','submitted','failed') and approved_at is not null and channel is not null)
     or (status = 'draft' and approved_at is null and channel is null) or status in ('withdrawn','refunded')) is false;
```

If a count is not 0, do not deploy yet; send me the rule and the count. Two notes:

- **One free grant per user** is a unique index, built in 0005. With a duplicate, the build fails, the runner stops the deploy ("left invalid indexes") and the old version keeps serving. The fix, while the ledger can still be edited (before 0006), is to turn each extra row into an adjustment, which keeps the balance: `update credit_ledger set reason = 'admin_adjustment', note = 'duplicate_free_grant' where id = '<extra row id>';`.
- The preferences check needs a function that 0007 creates, so it is checked after the deploy (step 4.3).

Once all of them are 0, a later migration validates these checks (they then also cover the old rows).

## 4. Deploy `wp/12` to sd1

1. Merge and deploy as usual. `sd1-api`'s pre-deploy runs 0005 to 0007 as the superuser (roles come in step 5). Expect one `migration applied` log line per file and then `migrations done`. 0005 builds its indexes without blocking writes.
2. If the pre-deploy fails, the old deployment keeps serving. The log names the file and the error. Send it to me; do not edit a migration file that already ran (CI and the runner both refuse).
3. Run the preferences post-check: `select user_id from profiles where preferences is not null and not preferences_valid(preferences);`. Expect no rows. A row here cannot be updated until its preferences are re-saved through the app (Settings > Preferences), which writes a valid shape.

## 5. Role cutover on sd1 (superuser access)

Until now the api and worker sign in as the superuser `postgres`. After this step each process has its own role (02-database 4.1): `kairos_api` and `kairos_worker` hold only the privilege matrix, neither may update or delete `credit_ledger`, the api cannot rewrite `inbound_emails`, and migrations run as `kairos_migrator`, which owns every table. Statement timeouts: api 10 s, worker 120 s, applier 5 s.

1. Railway > Postgres service > Variables: copy `DATABASE_PUBLIC_URL` (the superuser, `postgres`).
2. In Git Bash, from the repository root on the deployed commit:

   ```
   for r in migrator api worker readonly metrics backup; do printf '%s ' "$r"; openssl rand -hex 24; done > /tmp/kairos-roles.txt
   cat /tmp/kairos-roles.txt   # keep these in your password manager, then delete the file
   psql "<DATABASE_PUBLIC_URL>" -v ON_ERROR_STOP=1 \
     -v migrator_password="<migrator pw>" -v api_password="<api pw>" -v worker_password="<worker pw>" \
     -v readonly_password="<readonly pw>" -v metrics_password="<metrics pw>" -v backup_password="<backup pw>" \
     -f ops/provision-roles.sql
   ```

   Leave out `applier_password` to keep the applier's password from WP-04 (pass it only to rotate it). The script is safe to run again: it resets every runtime role's grants and changes a password only when you pass it. It moves the database and every table, function and type to `kairos_migrator`; the services keep working meanwhile because they still sign in as the superuser.
3. Check it. As the new api role (`psql "postgresql://kairos_api:<api pw>@<public host:port>/railway"`), run `update credit_ledger set note = note where false;`. Expected: `ERROR: permission denied for table credit_ledger`.
4. Railway variables, each pasted as a plain value (a `${{Postgres.DATABASE_URL}}` reference would resolve to the superuser again). Take the private URL (`postgresql://postgres:<pw>@postgres.railway.internal:5432/railway`) and replace `postgres:<pw>`:

   | Service | Variable | User | Host |
   |---|---|---|---|
   | `sd1-api` | `DATABASE_URL` | `kairos_api` | PgBouncer if step 2 found one, else direct |
   | `sd1-api` | `DATABASE_UNPOOLED_URL` | `kairos_migrator` | Direct (`postgres.railway.internal:5432`), never PgBouncer |
   | `sd1-worker` | `DATABASE_URL` | `kairos_worker` | PgBouncer if present, else direct |
   | `sd1-applier` | `DATABASE_URL` | `kairos_applier` (unchanged) | Unchanged |

   Do not set `DATABASE_UNPOOLED_URL` on the worker or the applier (the applier refuses to boot with it).
5. Redeploy `sd1-api` (its pre-deploy now runs as `kairos_migrator`; with nothing pending it only takes the lock and checks the applied files), then `sd1-worker`.
6. Smoke test as yourself: sign in, open the dashboard, add and confirm a fact, save preferences, queue a match, approve a draft. Then search the api and worker logs for `permission denied` and `42501`. The grant matrix was written from reading the code and the tests run as a superuser, so a missed grant shows exactly there; send me the table and the statement.
7. Rollback, per service: set `DATABASE_URL` back to the superuser URL and redeploy that service. The roles stay and do nothing.
8. Record the date and deploy ids in the WP-12 acceptance notes.

Each time a later migration adds a table, run the script again (step 5.2 without any password): migrations the migrator runs give the api and worker every right on a new table by default, and the script narrows them to the matrix. `kairos_readonly`, `kairos_metrics` and `kairos_backup` have no consumer yet; their URLs go to analytics, Grafana and `pgbackup` with WP-13 and WP-27.

## 6. Decide the migration numbering (one lane)

`decisions.md` gives one lane: the data lane (L4) allocates migration numbers. WP-12 takes `0005_fk_indexes`, `0006_backstops` and `0007_profiles`. Please confirm that a package merging after it takes the next free number (its file and journal entry renumbered on merge), and that a number is never changed once the file has run on sd1. The runner applies any journal entry that has not run yet, whatever its position, so merge order cannot skip one; CI's `migrations` job fails a pull request that edits, renames or deletes a migration already on `main`.

## 7. For CI and later packages, not owner steps

- CI gains a `migrations` job (expand-only linter, unchanged history, `drizzle-kit check`, no schema drift, apply to an empty database twice). Make it a required check next to `checks`.
- `server/test/applier-role.int.test.ts` now provisions every role and asserts the whole grant matrix (T-12); `schema-guards.int.test.ts` covers the backstops and the FK-index query; `migrator.int.test.ts` races two runs. They run in CI only (no local Postgres), and were type-checked but not run while writing.
- A migration that adds a table should be followed by a provisioning run on every environment; a new table that is not in the T-12 matrix fails that test until someone decides its grants.
