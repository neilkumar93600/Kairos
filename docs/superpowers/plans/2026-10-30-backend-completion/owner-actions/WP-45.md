# WP-45 owner actions: worker and queue hardening

The code is on branch `wp/45`. Steps 1 and 2 are checks to do before deploying it; step 3 is optional tuning.

## 1. Confirm Redis runs with `maxmemory-policy noeviction` (required, before deploying)

From now on the api, the worker and the applier refuse to boot unless Redis reports `maxmemory_policy:noeviction`. Under any other policy a full Redis silently drops queued jobs and their locks (an approved cloud send, a draft, a reply to tag) instead of refusing the write. The boot fails with `Redis maxmemory-policy is <policy>; BullMQ needs noeviction`, and also when Redis does not answer within 10 seconds.

1. Railway > Redis service > Data (or `railway connect Redis`), then run `INFO memory` and find the `maxmemory_policy:` line. `noeviction` is Redis's default, so it is probably already right.
2. If it says anything else, set it where the Redis service starts: Railway > Redis service > Settings > Deploy > Custom Start Command, add `--maxmemory-policy noeviction` to the `redis-server` command, and redeploy Redis [verify: the Railway Redis template's start command]. `CONFIG SET maxmemory-policy noeviction` works at once but is lost on the next Redis restart unless it is also in the start command.
3. Run `INFO memory` again and record the line in the WP-45 acceptance notes.

Deploy `wp/45` only after step 3. If a deploy fails anyway, the previous deployment keeps running and the deploy log names the policy.

## 2. Check the Postgres connection budget (before deploying)

The worker and the applier now size their Postgres pool to their job slots (scale-v12) instead of a fixed 10:

| Service | Pool per replica (defaults) |
|---|---|
| `sd1-api` | 10 (unchanged) |
| `sd1-worker` | 32: the sum of the queue concurrencies in `server/src/jobs/queues.ts` (30) plus 2 |
| `sd1-applier` | `APPLIER_CONCURRENCY` + 1, so 3 at the default of 2 |

With one replica each that is 45 connections, plus the migrator during a deploy. Run `show max_connections;` on the Postgres service and record it; it must stay above the sum over all replicas (Railway's default is 100 [verify]). If you add worker replicas, either check this again or lower the worker's slots with `QUEUE_CONCURRENCY` (step 3), which lowers its pool with them.

## 3. Optional variables

None is required; each has a default.

| Variable | Service | Default | What it does |
|---|---|---|---|
| `QUEUE_CONCURRENCY` | `sd1-worker` | empty | Per-queue job slots of one worker replica over the table in `jobs/queues.ts`, as `score-user=8,poll-boards=4`. An unknown queue name refuses the boot. The spec's scoring value is `score-user=8`; the default is 4, today's scoring concurrency, so model spend does not speed up on deploy |
| `APPLIER_RECYCLE_AFTER` | `sd1-applier` | 25 | Contexts one Chromium serves before it is replaced |
| `APPLIER_MEMORY_LIMIT_MB` | `sd1-applier` | 3600 | Container memory above which the applier recycles its browser |

## What changes in Redis

- `kairos:lane:score-user:<userId>`: each user's postings waiting to be scored. A key expires 7 days after its last write.
- `kairos:apply-gate:*`: cloud-apply slots per ATS (leases of 5 minutes), the per-minute start count and the 60-second cool-down after a 429. Each expires on its own.
- A new queue, `score-user`, with at most one waiting job per user; finished ones are removed at once.
