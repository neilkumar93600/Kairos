# WP-44 owner actions: Postmark streams, alert addresses, the link key and the delivery webhook

The code is on branch `wp/44`. It deploys without any of these: the new variables are optional, sign-in codes keep going out on today's token, and no email kind has a renderer yet (WP-24, WP-29 and WP-35 add them). Do steps 1 to 5 before the first of those ships. Staging first, then production. Each variable is a sealed Railway variable on the services named; `.railway/railway.ts` already declares the names.

## 1. Postmark: a broadcast stream

Postmark > your server > Message Streams > Create message stream > **Broadcasts**. Name it `Broadcasts`; its id (shown under the name, e.g. `broadcast`) is the value below. Digests, weekly reports and Autopilot summaries go there, so a burst of them never queues in front of sign-in codes on the transactional `outbound` stream.

| Variable | Services | Value |
|---|---|---|
| `POSTMARK_BROADCAST_STREAM` | api, worker | The stream id. Default `broadcast` |
| `POSTMARK_BROADCAST_TOKEN` | api, worker | Optional. Only if the broadcast stream lives on a **separate Postmark server** (recommended once volume grows, so a broadcast reputation problem cannot slow transactional mail): that server's API token. Unset: the transactional server's `POSTMARK_SERVER_TOKEN` is used |

On both streams, leave open and link tracking **off** (the code also sends `TrackOpens: false`, `TrackLinks: None`).

Postmark's outbound message search by Metadata must work on your plan (the notify job looks up `Metadata.k` before re-sending a stuck email). Check once: Postmark > Activity > search `metadata_k:` in the API explorer, or `curl -H "X-Postmark-Server-Token: ..." "https://api.postmarkapp.com/messages/outbound?count=1&offset=0&metadata_k=test"` answers 200. If it does not, tell the coordinator: the code then relies on the 10-minute lease alone, which can duplicate an email after a worker crash.

## 2. Alert addresses

| Variable | Services | Value |
|---|---|---|
| `ALERT_EMAIL_TO` | worker (also allowed on api) | Your ops inbox. Gets one email per `notify-reconcile` run that gave up on emails after 5 attempts. Unset: Sentry signal and log only |
| `CONTACT_ALERT_TO` | api, worker | Where contact-form messages go. Default `hello@kairos.app`; set it if that inbox is not read |

Use an address on a different provider from Postmark if you can, so an alert about broken sending is not lost to the same outage.

## 3. The link key and the public api origin

| Variable | Services | Value |
|---|---|---|
| `LINK_SIGNING_KEY` | api, worker. **Never** the applier (it refuses to boot with it) | `v1:` followed by `openssl rand -base64 32`. Its own key: the services refuse to boot if it equals a `DATA_KEKS` key |
| `API_PUBLIC_ORIGIN` | api, worker | The public Railway api origin, `https://...`, no path. Emailed links point here, and the api accepts form posts from it |

Rotation and compromise: `docs/runbook/keys.md` section 9.

## 4. Postmark delivery webhook (bounces and complaints)

1. Generate a secret: `openssl rand -hex 24`. Set it as `POSTMARK_EVENTS_SECRET` on the **api only**.
2. Postmark > server > each stream (`outbound` and the broadcast stream) > Webhooks > Add webhook. URL `<API_PUBLIC_ORIGIN>/api/webhooks/postmark-events?token=<the secret>`. Tick **Bounce**, **Spam complaint** and **Subscription change**. Nothing else.
3. Send a test Spam complaint from the webhook page: it answers 200 `{"recorded":true}`. With the secret unset or wrong it answers 403.

Rotate: set the new secret on the api, redeploy, then update both webhook URLs (a few minutes of 403s in between; Postmark retries them).
