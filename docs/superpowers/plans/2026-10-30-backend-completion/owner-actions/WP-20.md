# WP-20 owner actions: the evals key, its $5 cap, recording fixtures and labelling the golden sets

The code is on branch `wp/20`: the eval runner `server/evals/` (`npm run eval`, `npm run llm:record`), seed golden sets for the six enabled agents, render and post-validation tests for each agent under `server/test/agents/`, and `.github/workflows/evals.yml`. Deploying `wp/20` needs nothing from you; no service reads anything new.

What runs today without you: on every pull request that touches an agent, its golden set or the truth checks, the `evals (recorded fixtures)` job grades every case on its stored reply, with no network and no key. It fails on any invented detail (a number, employer, title, tool or link the cited facts lack, checked with the production `checkClaims`), any protected question that reaches a model, any protected detail in an output, any injection echo and any reply the gateway would reject. It also fails when a prompt changes, because every stored reply carries the fingerprint of the prompt it answered.

What waits for you: the stored replies are hand-written today (`"source": "hand_written"`). They prove the graders work, not that the prompts do. Real replies need the evals key (steps 2 to 4), and a set big enough to trust needs your labels (step 5).

## 2. The kairos-evals workspace and key

1. Anthropic Console > Settings > Workspaces. Create `kairos-evals` (WP-06 step 1 left it for this package).
2. Set its monthly spend limit to the figure from step 1, with email alerts at 50% and 80%.
3. Create one API key in it and keep it in your password manager as "Kairos evals key".

Never use a production or staging key for evals. The eval code reads only `ANTHROPIC_KEY_EVALS`, and only when `ALLOW_LLM_NETWORK=1` is set.

## 3. The GitHub environment and the $5 cap

1. GitHub > the repository > Settings > Environments > New environment, named `evals`.
2. Deployment branches and tags: leave "No restriction". Pull request runs use `refs/pull/<n>/merge`, which a branch rule would block. Do not add required reviewers unless you want to approve every live run by hand.
3. Environment secrets > Add secret: `ANTHROPIC_KEY_EVALS` = the key from step 2.
4. Do not add it as a repository secret, to Railway or to Vercel. No service reads it.

What happens then: the `evals (live, kairos-evals)` job runs on pull requests from this repository and on manual runs (Actions > Evals > Run workflow). It runs `npm run eval -- --live --repeat 3 --max-usd 5`. The cap is enforced in code: before each case the runner adds that case's worst cost (four sends on its model plus four on the tier-up model) to the run's spend so far, and stops if the total could pass USD 5. Pull requests from forks never get the secret, and the job is skipped for them, so they run only the fixture job. Until the secret exists, the live job prints a notice and passes.

## 4. Record the first real fixtures

From `server/` in a checkout of `wp/20`, once step 2 is done:

```bash
# Every case of every agent, then the same grading CI runs, with no network.
ALLOW_LLM_NETWORK=1 ANTHROPIC_KEY_EVALS=<key> npm run llm:record
npm run eval
# One agent, or one case:
ALLOW_LLM_NETWORK=1 ANTHROPIC_KEY_EVALS=<key> npm run llm:record -- --agent resume-tailor
ALLOW_LLM_NETWORK=1 ANTHROPIC_KEY_EVALS=<key> npm run llm:record -- --agent resume-tailor --case resume-tailor-0003
```

Each recorded reply overwrites `server/evals/<agent>/fixtures/<case>.json` with `"source": "recorded"`, the prompt fingerprint, a hash of the case input and the token usage. Only the synthetic case input is sent, never anything from production. The command prints the same table as `npm run eval`, and its own spend.

Before you commit the files, read the table:

- Every case passes: commit the fixtures in a pull request. The fixture job grades them.
- A case fails with `containment`, `fact_ids`, `sensitive` or `injection_echo`: the model made that mistake. Keep the fixture out of the commit and send me the line. The fix is a new prompt version, not a different label.
- A case fails because the label is wrong (for example a `mustNotClaim` word that a fact does support): fix the case, then record that case again.

Protected questions (`"abstain": "sensitive"`) get no fixture: production refuses them before any model call, so any request at all is the failure.

Record again after any prompt or schema change, or after editing a case's input. The fixture job says so: `fixture answered prompt v1 3dac8c06ecec; current is v2 ...; re-record with npm run llm:record -- --agent ... --case ...`.

## 5. Label the golden sets (about 6 hours)

The target is about 100 cases for each drafting agent: `resume-tailor`, `resume-writer`, `answer-drafter` and `cover-letter-writer`. Later, when you have time, 60 or more for `resume-parser` and 100 labelled pairs for `fit-scorer`. That is what makes "invented-detail rate 0" mean something.

How we split the work: I draft the cases from templates and synthetic personas, in batches of 25 per agent. You read and correct each one, which takes about 3 minutes a case. For each case, check:

1. **Input.** It is synthetic: an invented person and employer, `example.com` addresses and `555-01xx` phone numbers. Never paste your own resume, a real person's or a real posting that is not public. A test rejects any email or link not on `example.com` and any phone outside the 555 range.
2. **`mustNotClaim`.** List the details a tempting reply would invent that no fact supports: the posting's tools ("Kubernetes"), inflated numbers ("team of 40"), employers. The eval fails any claim containing one, even where `checkClaims` cannot see it.
3. **`mustNotAppear`.** List the sensitive or injected strings that may reach neither the model nor any output: the visa line, the CTC figure, the contact header.
4. **`abstain: "sensitive"`** (answer drafter only). Use it for every question a model must never answer: sponsorship, work authorization, salary, EEO, personal details, and profile fields (name, email, links). Add every phrasing you have seen on real forms. If `services/sensitive.ts` misses one, the eval fails, which is the point.
5. **`label`** (fit scorer only): your score from 0 to 100 for the pair.

Mix per drafting agent: about 70 ordinary cases, 20 adversarial or injection cases (an injection case names its clean twin in `cleanTwinOf`), and 10 regression or edge cases. After each batch, run step 4 for the new cases.

Reply "WP-20 labels: <agent> <count> reviewed" after each batch.

## 6. Decide whether the eval blocks merges (decision)

The workflow is path-filtered, so it does not run on pull requests that touch none of its paths. GitHub treats a required check that never ran as pending forever, so its jobs cannot be required checks as they are. A failing eval shows a red X on the pull request; nothing stops a merge if you ignore it.

| Option | How | For | Against |
|---|---|---|---|
| A. Leave as is | Path-filtered, not required | No change | Merging past a failed eval is possible |
| B. Require the fixture job (recommended) | I move the fixture job into `ci.yml` (it costs no money and about a minute); you add `evals (recorded fixtures)` as a required check on `main`. The live job stays path-filtered and advisory | A prompt change cannot merge until its replies are recorded and pass | Every pull request runs one more minute of CI |

Reply "WP-20 merge gate: option A" or "option B".
