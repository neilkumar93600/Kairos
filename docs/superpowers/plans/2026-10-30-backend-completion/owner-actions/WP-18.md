# WP-18 owner actions: encryption keys and the emergency kit

The code is on branch `wp/18`: `server/src/lib/crypto.ts` (AES-256-GCM under `DATA_KEKS`), the drill tool `server/scripts/data-keys.ts` and the runbook `docs/runbook/keys.md`. Nothing calls the library yet; WP-12 adds the first encrypted column (`profiles.sensitive_answers_enc`), then WP-17 and WP-24. Deploying `wp/18` needs nothing from you: `DATA_KEKS` stays optional until WP-12, but once set it must be well formed or the api and worker refuse to boot.

Do steps 1 to 5 before the WP-12 release that writes the first ciphertext. Data encrypted under a key that is not in the kit is one deleted variable away from gone, because Railway seals the variable and nobody can read it back.

## 1. Decide who holds the second copy (decision)

06-infrastructure question 12: who holds the second copy of `DATA_KEKS` and the backup key, and who can act if you are unreachable? The backup key is the pair of `age` private keys WP-13 creates for the encrypted database dumps. Both go in one kit, so one answer covers both.

| Option | How | For | Against |
|---|---|---|---|
| A. You only, two places | Password manager, plus a printed kit in a sealed envelope at a second place you control | Nobody else is trusted with anything | The bus factor stays 1. If you are unreachable, nobody can restore the service or read the encrypted data, and users lose their resume sources and replies |
| B. A trusted person holds the sealed offline copy (recommended) | Password manager, plus the printed kit in a tamper-evident envelope held by one person, with a one-page note. If your password manager has an emergency-access feature, add the same person with a waiting period of at least 7 days | Survives you being unreachable. A broken seal shows the kit was opened. The waiting period lets you refuse an access request you did not expect | You trust one person not to open or lose it, and you replace the envelope after every rotation |
| C. Professional custody | A bank safe-deposit box, or a sealed envelope held by your lawyer | Custody is someone's job | Days to reach, a yearly fee, and getting it out while you are incapacitated needs legal paperwork |

Recommendation: **B**, with a person who has no Railway, GitHub or database access, so nobody but you holds both the key and the ciphertext. A family member or your lawyer fits. They do not need to understand the contents. The note tells them to keep the envelope sealed unless you are unreachable, and then to hand it, with `docs/runbook/keys.md`, to whoever you name in the note to run the service. Also name a recovery contact on Railway (06-infrastructure 4.5).

Reply with "Kit holder: option <A, B or C>, <role, not a name if you prefer>". I record it in `decisions.md`.

## 2. Generate the production and staging keys

Follow `docs/runbook/keys.md` section 4 once for production and once for staging, in Git Bash from `server/` on a checkout of `wp/18`. In short:

```bash
printf 'v1:%s' "$(openssl rand -base64 32)" | clip   # new value on the clipboard, never on screen
# paste it into the password manager item "Kairos emergency kit" now
read -rs DATA_KEKS && export DATA_KEKS               # paste, Enter
npx tsx scripts/data-keys.ts check                   # prints: v1 <16 hex> current
unset DATA_KEKS
```

Production and staging must have different keys. Never put a production key in a local `.env`.

## 3. Railway variables

Set `DATA_KEKS` as a **sealed** variable on each service below, pasting the value directly. Do not put it in a shared variable group: a group can reach the applier.

| Service | `DATA_KEKS` |
|---|---|
| production api | production value |
| production worker | production value (the same as the api) |
| `sd1-api`, `sd1-worker` (staging) | staging value, the same on both |
| `sd1-applier`, any applier | never (a production applier refuses to boot with it) |
| `pgbackup`, Grafana, Vercel, GitHub Actions | never |

Redeploy the api and worker. If the deploy log shows `Invalid environment: DATA_KEKS: entry 1 ...`, the paste was damaged: paste it again.

## 4. Fill in the register and the kit

1. Send me the two fingerprints from step 2 (fingerprints only, never the keys), or write them into the register table in `docs/runbook/keys.md` section 2.
2. Print the kit sheet (`docs/runbook/keys.md` section 3) with the production and staging values and your recovery codes. Seal it and give it to the holder from step 1. Leave space for the backup `age` keys; you add them when WP-13 creates them, and replace the envelope then.

## 5. Run the first drill

`docs/runbook/keys.md` section 6, steps 1, 2, 4 and 5, from the sealed copy: open it, run `check`, compare the fingerprints, reseal it in a new envelope. Step 3 (decrypt a real row) waits until WP-12's column holds data; I will ask for it then. Reply "WP-18 drill passed <date>".

## 6. Calendar

Add two yearly reminders, a year from step 2: rotate `DATA_KEKS` (`docs/runbook/keys.md` 5.1) and run the drill (section 6). Doing both on the same day is fine: the drill is the last step of a rotation.
