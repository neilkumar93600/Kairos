# WP-42 owner actions: lifecycle schema expand

The code is on branch `wp/42`. It adds four migrations (numbered 0009 to 0012 on the branch; the merge may renumber them):
`lifecycle_expand` (columns, three new tables, checks, guards), `match_below_bar` (one enum value), `lifecycle_backfill`
(B-5, B-8, B-10, tracker items and the history) and `lifecycle_indexes` (indexes built concurrently, then the checks
validated). Nothing changes for users: today's code writes the new columns only where a check requires it.

## 0. A decision made for you (confirm or overrule)

The schema-authority decision is open. WP-42 follows the plan's recommendation, **"PRD authoritative, one numbering lane"**:
`application_events` is keyed by `tracker_item_id` with an `application_id` link, and `tracker_items` lands now because
of that. If you choose "spec authoritative" instead, a later migration adds `NOT NULL` to `application_events.application_id`
and drops the tracker key; nothing in WP-42's data would be lost. Record your choice in `decisions.md`.

## 1. Before deploying: count and pre-check (sd1, as the superuser)

The backfill is SQL inside a migration, which the design allows only while each table is below 100,000 rows:

```sql
select 'companies' t, count(*) from companies union all select 'jobs', count(*) from jobs
union all select 'matches', count(*) from matches union all select 'applications', count(*) from applications;
```

If `jobs` or `matches` is over 100,000, stop and tell the data lane: the backfill must move to batches first.

Then the checks the backfill's own updates will meet. A `NOT VALID` check still holds any row an update touches, so every
count here must be 0 **before** the deploy, or the migration fails (and the release before it keeps running):

```sql
select 'companies_name_ck' as rule, count(*) from companies where char_length(name) not between 1 and 200
union all select 'companies_board_token_ck', count(*) from companies where board_token !~ '^[A-Za-z0-9_.-]{1,100}$'
union all select 'matches_score_ck', count(*) from matches where score is not null and score not between 0 and 100
union all select 'applications_json_ck', count(*) from applications
  where (jsonb_typeof(resume_lines) = 'array' and jsonb_array_length(resume_lines) <= 200
     and jsonb_typeof(answers) = 'array' and jsonb_array_length(answers) <= 200
     and (receipt is null or jsonb_typeof(receipt) = 'object')) is not true
union all select 'applications_text_ck', count(*) from applications where char_length(failure_reason) > 500
union all select 'pg_trgm available', count(*) - 1 from pg_available_extensions where name = 'pg_trgm';
```

The last row is 0 when `pg_trgm` can be installed (it is a trusted extension: `kairos_migrator`, the database owner, may
create it). A non-zero row elsewhere names rows to fix by hand first; ask before deleting anything.

What the deploy changes in existing data, so you are not surprised:

- Jobs stored before WP-04 with an employer's own apply link get the hosted-form link the applier accepts
  (`https://job-boards.greenhouse.io/embed/job_app?for=<board>&token=<id>` and the Lever and Ashby equivalents).
- Inactive companies that were never polled are marked `import_pending` (pasted boards); other inactive ones `owner`,
  or `board_not_found` after a 404.
- Pipeline matches that failed the hard filters are deleted (they were never meant to be stored); imported matches are
  marked as imports.
- Every application gets a tracker item and its history events (drafted, approved, sent, failed, withdrawn), approval
  facts, a failure code, a draft state and, when it was ever sent or claimed, one attempt row. A legacy cloud claim still
  `submitting` becomes an open attempt that WP-29's sweeper will settle as unconfirmed.

## 2. Deploy, then rerun the roles script

Deploy as usual (the api's pre-deploy runs the migrations). `lifecycle_indexes` builds 17 indexes concurrently; it
blocks no reads or writes and may wait up to 4 minutes per index behind a long transaction. Then run
`ops/provision-roles.sql` again (the command is at the top of the file): it grants the three new tables and narrows the
wide default the migrator role gave them. Until then `kairos_readonly` cannot see them and the api and worker roles
hold more than they should.

## 3. Backfill the job hints (B-6)

From `server/`, with the Postgres service's public URL (Railway > Postgres > Connect):

```
DATABASE_URL="<public url>" node --import tsx --import ./scripts/md-register.mjs scripts/backfill-job-hints.ts
```

It prints a running count and stops at `done`. It is safe to stop and run again, and safe beside the poller. New jobs
already get these columns from the poller and the import route.

## 4. Validate the remaining checks (when step 1 found nothing)

```sql
alter table companies validate constraint companies_name_ck;
alter table companies validate constraint companies_board_token_ck;
alter table matches validate constraint matches_score_ck;
alter table applications validate constraint applications_json_ck;
alter table applications validate constraint applications_text_ck;
```

Each takes a lock that blocks no reads or writes. An error names the rule; send it to the data lane.
