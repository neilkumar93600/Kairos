# WP-06 owner actions: AI spend ceilings and turning the gateway on

The code is on branch `wp/06`. Once deployed, every AI route has a per-feature daily allowance kept in Postgres (Free: 10 suggestions, 5 tailors, 10 drafts, 3 imports a day), the scoring loop scores only users active in the last 14 days with credits and unpaused billing, at most `dailyScoringCap` pairs per user per day, and `PAUSE_SCORING` stops it. Those controls work on today's legacy client too. The per-user spend caps, the per-agent envelopes, the global ceiling and the `llm_calls` ledger only work once `LLM_GATEWAY=anthropic`, and that needs your keys and one paid smoke run. Do the steps in order; nothing here is needed before deploying `wp/06` itself (the default stays `LLM_GATEWAY=legacy`).

## 1. Anthropic workspaces, keys and console limits

1. Anthropic Console > Settings > Workspaces. Create `kairos-staging`, `kairos-prod-interactive` and `kairos-prod-batch` (01-architecture B.9.1; `kairos-evals` can wait for the eval harness).
2. On each workspace set a monthly spend limit and email alerts at 50% and 80%. Closed-beta suggestion: staging USD 10, interactive USD 30, batch USD 20, inside the organization limit you set in WP-00. These are the backstop if every check in code fails.
3. Create one API key per workspace and keep them in your password manager.

## 2. USER_HASH_KEY

Generate once: `openssl rand -base64 32`. Use one value per environment (staging and production may differ) and keep it in your password manager. It keys `llm_calls.user_hash` and the per-user prompt fence; changing it later only re-keys rows going forward, so do not rotate it casually.

## 3. Railway variables

| Service | Variables |
|---|---|
| `sd1-api` (staging) | `ANTHROPIC_KEY_INTERACTIVE` = staging key, `USER_HASH_KEY` |
| `sd1-worker` (staging) | `ANTHROPIC_KEY_INTERACTIVE` = staging key, `ANTHROPIC_KEY_BATCH` = staging key, `USER_HASH_KEY` (same value as the api) |
| production api | `ANTHROPIC_KEY_INTERACTIVE` = `kairos-prod-interactive` key, `USER_HASH_KEY` |
| production worker | `ANTHROPIC_KEY_INTERACTIVE` = `kairos-prod-interactive` key, `ANTHROPIC_KEY_BATCH` = `kairos-prod-batch` key, `USER_HASH_KEY` (same value as the api) |
| `sd1-applier` | none of these, ever |

Never put `ANTHROPIC_KEY_BATCH` on an api service (03-agent-runtime 16.1). Leave `ANTHROPIC_API_KEY` where it is until step 6: the legacy path still reads it. Optional on every api and worker: `LLM_SHED_LEVEL` (0 to 3, default 0) to shed AI work by hand, and `PAUSE_SCORING=true` to stop scoring new postings.

## 4. Approve the S-A1 spend, then run the smoke

The smoke makes one real call per agent (six agents) plus two repeat scorer calls, with synthetic text only (no real person or employer). Expected cost is about USD 0.02 (the agents' expected cost per call); the script refuses any call that could take the total past USD 0.50 (`LLM_SMOKE_MAX_USD`). Reply "S-A1 spend approved" before running it.

From `server/` in a checkout of `wp/06`, with the staging keys:

```bash
# No network, no key: proves every request builds.
LLM_SMOKE_DRY=1 npm run llm:smoke
# The live run.
ALLOW_LLM_NETWORK=1 ANTHROPIC_KEY_INTERACTIVE=<staging key> ANTHROPIC_KEY_BATCH=<staging key> USER_HASH_KEY=<value> npm run llm:smoke
```

It passes when it ends with `all agents passed` and exits 0. Send me the output (it holds no personal data). I check that every agent answered `ok` (every schema snapshot and thinking setting was accepted), that the two repeat `fit-scorer` calls show a cache share (target at least 55%), and the cost per call against the agent specs. A `FAIL ... invalid_request` line means a request shape was refused: do not flip the gateway; send me the output.

## 5. Confirm the 429 decision

The spent allowance answers `429 rate_limited` with `details.reason = "daily_allowance"` and `resetsAt`, and `402` stays "no credits" (decisions.md, "How are per-feature daily AI limits answered and capped?"). A spend stop on the service side answers `429` with `reason: "service_budget"`. Reply "429 confirmed", or tell me to change it before the web copy ships (frontend-handoff/WP-06.md).

## 6. Turn the gateway on: staging, then production

1. Staging: set `LLM_GATEWAY=anthropic` on `sd1-api` and `sd1-worker` and redeploy both. Use the web app for ten minutes: one resume suggestion, one tailor, one drafted answer, one resume upload. Then in the Railway Postgres query tab:

   ```sql
   select agent_id, model, status, error_code, count(*), sum(cost_usd), count(user_hash) as with_user
   from llm_calls where created_at > now() - interval '1 hour' group by 1, 2, 3, 4 order by 1;
   select * from llm_cost_daily where day = (now() at time zone 'utc')::date;
   ```

   Every row should have `with_user` equal to its count (each call carries a `user_hash`), statuses should be `ok`, and `llm_cost_daily` should fill within two minutes (the worker rolls it up every minute). A response with `Kairos-Allowance` in the browser's network tab confirms the allowance header.
2. Leave staging on for a day. If nothing looks wrong, do the same on production.
3. A week after production is stable, delete `ANTHROPIC_API_KEY` from every service; the legacy client is removed in P3.

To go back at any point: set `LLM_GATEWAY=legacy` and redeploy. To stop spend fast without a deploy of code: `PAUSE_SCORING=true` (scoring), `LLM_SHED_LEVEL=3` (all scoring and resume suggestions), or the console workspace limit (everything).

## 7. Check the llm_calls partitions

Migration 0002 created weekly `llm_calls` partitions for the seven weeks after it was applied. Creating new ones on a schedule belongs to WP-09. Until WP-09 ships, check once a month that a partition exists for the coming weeks:

```sql
select relname from pg_class where relname like 'llm_calls_2%' order by relname desc limit 3;
```

If the newest is less than two weeks ahead, run `select llm_calls_ensure_partitions(6);`.
