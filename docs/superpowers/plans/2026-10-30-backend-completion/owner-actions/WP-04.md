# WP-04 owner actions: applier containment

The code is on branch `wp/04`. These steps need Railway and the database superuser, so only the owner can do them. Do steps 1 and 2 before deploying `wp/04` to `sd1-applier`. From this package on, a production applier refuses to boot while any auth, Stripe, model, mail or webhook secret is set on it.

## 1. Strip `sd1-applier` down to its own variables (before deploying)

Railway > project > service `sd1-applier` > Variables. Delete each of these if present. Also open "Shared Variables" and check that no shared group or `${{...}}` reference brings them back:

`BETTER_AUTH_SECRET`, `INBOUND_WEBHOOK_SECRET`, `GOOGLE_CLIENT_SECRET`, `POSTMARK_SERVER_TOKEN`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `ANTHROPIC_API_KEY`, `ANTHROPIC_KEY_INTERACTIVE`, `ANTHROPIC_KEY_BATCH`, `ANTHROPIC_KEY_EVALS`, `USER_HASH_KEY`, `DATA_KEKS`, `LINK_SIGNING_KEY`.

The applier ignores the other api variables (`WEB_ORIGIN`, `STRIPE_PRICES`, `EMAIL_FROM` and so on), so delete them too. Keep only these:

| Variable | Value |
|---|---|
| `DATABASE_URL` | The `kairos_applier` URL from step 2 |
| `REDIS_URL` | Unchanged |
| `OWNER_USER_IDS` | The same value as on `sd1-api` |
| `CLOUD_APPLIER_OPEN` | `0` (step 4) |
| `APPLIER_CHROMIUM_SANDBOX` | `1` (step 3) |
| `APPLIER_CONCURRENCY`, `LOG_LEVEL` | Optional |

`NODE_ENV=production` and `FILLER_SCRIPT_PATH` come from the image. Leave `CHROMIUM_EXECUTABLE_PATH` unset; the Playwright image finds its own Chromium.

If a forbidden key is still set, the deploy log shows `Invalid environment: STRIPE_SECRET_KEY: must not be set on the applier` (the name only, never the value) and the service restarts in a loop. Delete the named variable and redeploy.

These secrets sat on a process that opened employer pages with no Chromium sandbox. If the cloud applier ever ran for anyone but you, or on a board you did not curate, rotate the Stripe, Anthropic and Postmark keys on `sd1-api` and `sd1-worker`. Leave `BETTER_AUTH_SECRET` alone (rotating it signs everyone out and makes the stored Google tokens unreadable, WP-02).

## 2. Create the `kairos_applier` role and point `sd1-applier` at it

The applier now connects as a role that can read applications, three columns of `jobs` and three of `subscriptions`. It can update five columns of `applications` and insert the one ledger debit. It cannot read `user`, `session`, `account`, profiles, facts, inbound mail or any other ledger column.

1. Railway > Postgres service > Variables: copy `DATABASE_PUBLIC_URL`. It signs in as the superuser `postgres`.
2. In Git Bash (it has `openssl`; any `psql` client works), from the repository root on branch `wp/04`:

   ```
   APPLIER_PW=$(openssl rand -hex 24)
   psql "<DATABASE_PUBLIC_URL>" -v ON_ERROR_STOP=1 -v applier_password="$APPLIER_PW" -f ops/provision-roles.sql
   echo "$APPLIER_PW"
   ```

   Using `railway connect Postgres` instead: in its psql prompt, run `\set applier_password '<paste a long random value>'` and then `\i ops/provision-roles.sql`.
   The script is safe to run again. It resets the role's grants each time, and sets the password to whatever you pass, so update `DATABASE_URL` if you pass a new one. Run it after migrations (it names objects from migration 0002, which is already on sd1).
3. Railway > `sd1-applier` > Variables > `DATABASE_URL`. Take the Postgres service's private `DATABASE_URL` (`postgresql://postgres:<pw>@postgres.railway.internal:5432/railway`) and replace `postgres:<pw>` with `kairos_applier:<APPLIER_PW>`. Paste it as a plain value. A `${{Postgres.DATABASE_URL}}` reference would resolve to the superuser again.
4. Check it. Connect as the new role (`psql "postgresql://kairos_applier:<APPLIER_PW>@<public host:port>/railway"`) and run `select id from "user" limit 1;`. Expected: `ERROR: permission denied for table user`.

The script also takes `EXECUTE` on the three `SECURITY DEFINER` partition functions of migration 0002 away from `PUBLIC`. Without that, any login could drop `llm_calls` partitions. The api and worker connect as the owner and are unaffected.

## 3. Spike S-AP4: the Chromium sandbox on Railway

Deploy `sd1-applier` with `APPLIER_CHROMIUM_SANDBOX=1`. Within about 10 seconds of `applier started`, the deploy log shows one of two lines:

- `chromium launched` with `"sandbox":true`. S-AP4 passed. Record the date and deploy id in the WP-04 acceptance notes. Nothing else to do.
- `chromium failed to launch`, with `No usable sandbox` or a namespace error in the message. Railway's container does not let Chromium sandbox itself. Then:
  1. Sign a written risk acceptance (template below) and keep it with `decisions.md`.
  2. Set `APPLIER_CHROMIUM_SANDBOX=0` and redeploy. Every boot then logs a warning that the sandbox is off.

Template:

> I accept that the Kairos cloud applier runs Chromium without its own sandbox on Railway (spike S-AP4 failed on <date>, deploy <id>). In place: the applier holds no auth, Stripe, model or mail secret; it connects as kairos_applier; it opens only the five ATS hosts, blocks requests to internal addresses and IP literals, and uses a fresh browser context per application. Residual risk: a Chromium exploit on an ATS page runs code in the applier container, which can read every user's applications (answers included), write the five granted columns, insert credit debits and reach Redis. I will review this by <date>, or sooner when the P5 definer-function role or a sandbox-capable host lands. Signed, <name>, <date>.

## 4. Keep the cloud channel owner-only until acceptance

Leave `CLOUD_APPLIER_OPEN=0` on both `sd1-api` and `sd1-applier`. Once WP-04 passes on staging and S-AP4 has passed or been signed off, open it to Pro and Max: set `CLOUD_APPLIER_OPEN=1` on both services and redeploy both. The api gates approval and the applier re-checks the plan when it claims a row. Owners keep access on any plan either way.

One behaviour changes. A non-owner's cloud row that is already approved now fails at claim with the "Your plan no longer includes the cloud applier" message, where WP-00 stored "The cloud applier is not open yet". Either way no browser starts and no credit is used.

## 5. Staging acceptance (as the owner)

1. Approve one cloud application as the owner, for a posting you really want to apply to.
2. Check the row: `select status, failure_reason, submitted_at from applications where id = '<id>';`. Expect `submitted`, or `failed` with one of the six fixed sentences from `server/src/services/submissions.ts` (`FAILURE_MESSAGES`). Never an exception message or a URL.
3. Expect the "We could not confirm whether the employer received this application" sentence on Greenhouse and Lever. Their confirmation page is a new page load, which ends the filler call, so the applier cannot see the confirmation. It records the run as unconfirmed (needs_check) and charges no credit, because it will not guess. Check your email for the employer's confirmation. Detecting these confirmations is spike S-AP2 (WP-29).
4. Record the date, deploy id and outcome in the WP-04 acceptance notes.

## 6. Optional: Lever and Ashby jobs stored before this change

New and imported postings get apply URLs built from the board token and posting id. Rows stored earlier keep the URL the board sent. This lists the open rows where the two differ:

```sql
select j.id, c.ats, c.board_token, j.external_id, j.apply_url
from jobs j join companies c on c.id = j.company_id
where j.closed_at is null and (
  (c.ats = 'lever' and j.apply_url <> 'https://jobs.lever.co/' || c.board_token || '/' || j.external_id || '/apply')
  or (c.ats = 'ashby' and j.apply_url <> 'https://jobs.ashbyhq.com/' || c.board_token || '/' || j.external_id || '/application'));
```

If it returns nothing, you are done. Otherwise, the applier already refuses any row whose host is off the allowlist (failed, no credit). To rewrite the rows, run both statements:

```sql
update jobs j set apply_url = 'https://jobs.lever.co/' || c.board_token || '/' || j.external_id || '/apply'
from companies c
where c.id = j.company_id and c.ats = 'lever' and j.closed_at is null
  and c.board_token ~ '^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$'
  and j.external_id ~* '^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$';

update jobs j set apply_url = 'https://jobs.ashbyhq.com/' || c.board_token || '/' || j.external_id || '/application'
from companies c
where c.id = j.company_id and c.ats = 'ashby' and j.closed_at is null
  and c.board_token ~ '^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$'
  and j.external_id ~* '^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$';
```

## 7. For WP-01 (CI), not an owner step

- `server/test/applier-role.int.test.ts` runs `ops/provision-roles.sql`, so the CI Postgres user must be able to create roles (the official image's `POSTGRES_USER` can). `kairos_applier` must be able to sign in with its password (the image's default `pg_hba` allows it).
- `server/test/cloud-apply.browser.test.ts` (the SSRF, challenge, CSP and real-filler fixtures) skips when Chromium is missing. Add `npx playwright install chromium`, at the `playwright-core` version, to the CI test job so they run on every pull request.
- Rebuild the applier image on every Playwright release (CISO mustFix 1(7)). WP-01 pins it by digest.

## What this package does not cover

- The egress proxy (07-cloud-applier 7.5, platform-69). The route check blocks IP literals and private-network names. It cannot block a public name that resolves to a private address, and a redirect is checked only where it lands.
- Definer functions that limit the role to the attempt it claimed (P5), `submit_seen` interception (S-AP2), the posting re-fetch at claim, browser recycling (WP-45), and the stuck-`submitting` sweeper (WP-09).
