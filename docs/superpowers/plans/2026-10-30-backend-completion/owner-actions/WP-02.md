# WP-02 owner actions: working sign-in on staging and production

The code is on branch `wp/02`. These steps need consoles and secrets, so only the owner can do them. Do steps 1 to 4 before deploying `wp/02` to `sd1-api`: from this package on, a production api refuses to boot unless `BETTER_AUTH_URL` and `WEB_ORIGIN` are the same bare `https` origin (no path) and every `CSRF_ALLOWED_ORIGINS` entry is `https`.

## 1. Confirm the provider decision

Beta sign-in is email+OTP and Google only (decisions.md, "Which sign-in methods must work at beta?"). Apple, GitHub and LinkedIn stay hidden until WP-38. Reply "confirmed" or name a change.

## 2. Railway, service `sd1-api` (staging, and the production api when it exists)

Set these values. They are values only; no secret is shown here.

| Variable | Value |
|---|---|
| `BETTER_AUTH_URL` | The exact Vercel production origin of project `kairos`, for example `https://kairos.vercel.app` or the custom domain. No trailing slash, no path. |
| `WEB_ORIGIN` | The same value as `BETTER_AUTH_URL`. |
| `CSRF_ALLOWED_ORIGINS` | Empty on production. On staging, optionally a comma list of exact preview origins you sign in from, for example the branch alias `https://kairos-git-main-<team>.vercel.app`. Wildcards, paths and (in production) `http://` entries are refused at boot. |
| `EXTENSION_ORIGIN` | `chrome-extension://<published extension id>` once the extension id is fixed. |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | From step 3. Google is offered only when both are set. |
| `MAIL_SINK_FILE` | Leave unset. It is refused in production. |

`BETTER_AUTH_SECRET` stays as it is. Changing it would make stored Google tokens unreadable, because they are now encrypted with it.

## 3. Google Cloud console (OAuth client, type "Web application")

1. Authorized JavaScript origins: the Vercel production origin (and every origin listed in `CSRF_ALLOWED_ORIGINS`).
2. Authorized redirect URIs: `<WEB_ORIGIN>/api/auth/callback/google`, for example `https://kairos.vercel.app/api/auth/callback/google`. It must be the web origin, not the Railway URL; the Railway URL fails with `state_mismatch`.
3. Scopes: leave the defaults (openid, email, profile). Never add a Gmail scope: the user's mailbox is never read.
4. OAuth consent screen: app name Kairos and the support email. Move it to "In production" before inviting beta users (in testing mode only listed test users can sign in).

## 4. Vercel, project `kairos` (web/)

Set `API_ORIGIN` to the Railway api origin (for example `https://sd1-api-staging.up.railway.app`) for Production and for Preview. The rewrite is fixed at build time, so redeploy after setting it. The build guard that fails without it is a web change (frontend-handoff/WP-02.md).

## 5. Run the smoke test through the Vercel domain

From the repository root, with an inbox you can read (the script adds `+smoke-<time>` to the address, so Gmail and most providers deliver it):

```
SMOKE_BASE_URL=https://<vercel production domain> SMOKE_EMAIL=<you@example.com> node scripts/smoke.mjs
```

Type the six-digit code when asked. Expected output ends with `smoke passed (probe id smoke-...)`. The script signs up, verifies, signs in, reads `GET /api/me`, checks the Google redirect URI and deletes its user. If a step fails after sign-up, it still tries to delete the user and prints `cleanup: deleted <email>`. If it prints `cleanup failed, remove <email> by hand` (for example when the code was never verified), delete that user row in the database by email.

Then finish Google by hand: open `<vercel domain>/login`, press "Continue with Google", and confirm you land signed in on the dashboard. Record both results (date, deploy id, pass or fail) in the WP-02 acceptance notes.

## 6. Spike S-B1 header probe (same run)

Every smoke request carries the header `x-kairos-probe: <probe id>`. In the Railway logs of `sd1-api`, search for that probe id. The request log line shows `req.headers`. Record for one request: `x-forwarded-for` (every entry, in order), `x-real-ip`, `x-forwarded-host`, `x-forwarded-proto`, whether `x-vercel-id` is present, and `req.remoteAddress`. Run the script once more against the Railway URL directly (`SMOKE_BASE_URL=<railway url> SMOKE_WEB_ORIGIN=<vercel origin>`) to record the direct (extension) chain. These two chains set the hop counts for the client-IP fix (CISO mustFix 4); do not set any hop count before they are recorded.

## 8. One-off: clear Google tokens stored before this deploy

From `wp/02` on, Google access and refresh tokens are stored encrypted, and the id token is not stored at all. Rows written before that stay in plain text until the user signs in with Google again. Nothing in the api reads these tokens (they are used for sign-in only), so after deploying `wp/02`, run this once against the `sd1-api` database:

```
UPDATE account SET access_token = NULL, refresh_token = NULL, id_token = NULL WHERE provider_id = 'google';
```

## 9. For WP-00 (CI), not an owner step

`.github/workflows/ci.yml` has no Postgres service. So every `*.int.test.ts` skips in CI and cannot gate a pull request yet, including `server/test/auth.int.test.ts` (pre-hijack, token encryption, id token, reset revocation, the smoke run and its cleanup). When WP-00 adds the Postgres service, it should also set `TEST_DATABASE_URL` and `REQUIRE_TEST_DB=1` on the test step. With `REQUIRE_TEST_DB=1`, `server/test/test-db-helper.test.ts` fails the run if the database URL is missing, so the integration tests can never skip silently again.
