# WP-10 owner actions: billing correctness

The code is on branch `wp/10`. These steps need the Stripe dashboard and Railway, so only the owner can do them. Do step 1 before the first test-mode checkout on staging. Steps 2 and 3 are decisions; the code ships safe defaults (no $0 grants, refunds and disputes alert only) until you answer.

What changed for you:

- A $0 invoice (a 100% coupon or a trial) no longer grants credits, unless its coupon is on the allowlist in step 2.
- A paid invoice or subscription the server cannot place (a price missing from `STRIPE_PRICES`, a customer no Kairos user owns) now answers 500, so Stripe keeps retrying instead of the money being silently dropped. See step 6 for what to do when that happens.
- A user whose renewal fails keeps the paid plan for 7 days, then works as Free until the card is fixed (the stored plan comes back at once).
- A second checkout by someone who already has a live subscription goes to the billing portal instead of creating a second subscription.
- A production api with a live key (`sk_live_...`) and no `STRIPE_WEBHOOK_SECRET` refuses to boot.

## 1. Register the Stripe test-mode webhook (the nine event types)

1. Stripe dashboard, **test mode** on > Developers > Webhooks (or Workbench > Event destinations) > Add endpoint.
2. Endpoint URL: `https://<sd1-api public Railway domain>/api/webhooks/stripe`. Use the Railway api host directly, not the Vercel origin: Stripe signs the exact bytes, so nothing should sit in between.
3. API version: `2026-09-30.endive`, the version the server's Stripe SDK (23.0.0) is pinned to, so event shapes match the code.
4. Select exactly these nine events:
   - `customer.subscription.created`
   - `customer.subscription.updated`
   - `customer.subscription.deleted`
   - `customer.subscription.paused`
   - `customer.subscription.resumed`
   - `invoice.paid`
   - `invoice.payment_failed`
   - `charge.refunded`
   - `charge.dispute.created`
5. Save, reveal the signing secret (`whsec_...`) and set it on Railway > `sd1-api` > Variables > `STRIPE_WEBHOOK_SECRET`. Redeploy `sd1-api`.
6. Check that `STRIPE_PRICES` on `sd1-api` lists all nine test-mode prices (`starter|pro|max` x `week|month|quarter`), for example `{"starter:month":"price_...","pro:month":"price_...",...}`.
7. Test with a real test-mode checkout: sign in on staging, Billing > pick a plan, pay with card `4242 4242 4242 4242`, any future date, any CVC. In Stripe > the endpoint > Event deliveries, every event should show 200, and `GET /api/me` should show the plan and the new credits.
   - Do not use the dashboard's "Send test event" for `invoice.*` or `customer.subscription.*`: those fixtures carry no Kairos price or user, so the server answers 500 on purpose and Stripe retries them. `stripe trigger` from the Stripe CLI has the same problem. A real test checkout is the test.
   - To test a failed renewal: create the test customer on a test clock (Stripe > Billing > Test clocks), subscribe, change the card in the portal to `4000 0000 0000 0341` (attaches, then fails on charge), and advance the clock past the renewal. The subscription goes `past_due` and the plan stays for 7 days.
8. Customer portal: Stripe > Settings > Billing > Customer portal (test mode). Allow updating the payment method, cancelling, and switching between the nine prices. The 409 double-checkout redirect sends users here. Set downgrades to take effect **at the end of the billing period** (no proration credit): a renewal paid entirely from proration credit is a $0 invoice, and a $0 invoice grants no credits, so with immediate downgrades a Max-to-Starter user could go a cycle or two without credits.
9. Stripe > Settings > Checkout and Payment Links (under Payments) > Subscriptions: turn on **"Limit customers to one subscription"**. The server already refuses a second checkout once a subscription is live; this setting also covers two checkout tabs opened before either was paid. The menu label may differ slightly in your dashboard.

Rolling the signing secret later: on the endpoint choose "Roll secret" with an expiry (for example 24 hours). Set `STRIPE_WEBHOOK_SECRET_PREVIOUS` to the old value and `STRIPE_WEBHOOK_SECRET` to the new one, redeploy, and delete `STRIPE_WEBHOOK_SECRET_PREVIOUS` after the expiry. Signatures older than 300 seconds are always refused.

Going live: repeat this step in live mode, with live prices in `STRIPE_PRICES` and the live `whsec_...`. The api will not boot with `sk_live_...` until `STRIPE_WEBHOOK_SECRET` is set.

## 2. Coupon allowlist (decision; default: empty)

`STRIPE_GRANT_COUPONS` is a comma-separated list of Stripe coupon ids whose $0 invoices still grant a full cycle of credits. Empty (the default) means a $0 invoice never grants. Promotion codes stay off in Checkout (WP-00), so a coupon reaches a customer only when you apply it.

If you want a beta coupon that grants credits:

1. Stripe > Product catalog > Coupons > New. Choose the id yourself (for example `BETA100`). Prefer duration "once" or "repeating" for a few months: every $0 renewal under a "forever" 100% coupon grants a full cycle.
2. Apply it to the customer or to the subscription, not to a single line item: the server reads the invoice-level discounts.
3. Railway > `sd1-api` > Variables > `STRIPE_GRANT_COUPONS` = `BETA100` (several ids comma-separated). Redeploy.

Reply with the list, or "keep empty".

## 3. Refund and dispute policy (decision; default: alert only)

Today a refund (`charge.refunded`) or a dispute (`charge.dispute.created`) is recorded and logged at error level with the message `stripe refund or dispute: no credits changed, operator decision needed`, carrying the event id, charge or dispute id and amount. No credits are taken back automatically, and the plan is unchanged until Stripe cancels or changes the subscription.

Recommended for the paid beta (_db/billing.md Q-4):

- Refund: you decide by hand whether to remove unused credits. There is no operator tool yet (billing-43); until then ask for a one-off `admin_adjustment` row. If you refund to end the relationship, cancel the subscription in Stripe too.
- Dispute: respond in Stripe before its deadline (shown on the dispute, usually 7 to 21 days) and cancel the subscription.
- Make sure Stripe emails you about disputes and refunds (your Stripe user settings, communication or email notification preferences). Until WP-11 adds Railway log alerts, that email is your page.

Reply "alert only is fine" or describe the policy you want (for example "a refund removes the credits granted by that invoice, never below the credits already spent").

## 4. Confirm the 7-day past_due grace

A failed renewal keeps the paid plan for 7 days from the moment the subscription turned `past_due`, then the user works as Free (cloud applier, cover letters and extra resume profiles off) until the card is fixed. No credits are granted while past_due. Reply "confirmed" or give another number of days.

The deploy runs migration `0003_billing_past_due_since`. Anyone already `past_due` at deploy time starts their 7 days at deploy time. To see who that is, in the Railway Postgres query tab:

```sql
select user_id, plan, status, past_due_since from subscriptions where status = 'past_due';
```

## 5. Do not change a price id in place

`STRIPE_PRICES` holds one price per plan and interval. A subscription still on a price that is no longer in that map now makes its events answer 500 (they used to be dropped silently). When you change a price, create the new price, move existing subscribers to it in Stripe (or wait until they have all moved), and only then replace the id in `STRIPE_PRICES`. If you need old and new prices to coexist, ask for multi-id support.

## 6. When the Stripe webhook answers 500

Stripe retries for up to 3 days and emails you if an endpoint keeps failing; it can disable an endpoint that fails for days. Look in the `sd1-api` logs for `anomaly_`:

- `anomaly_unmapped_price`: the price on that invoice or subscription is missing from `STRIPE_PRICES`. Add it, redeploy, and the next retry succeeds (or press "Resend" on the event in Stripe).
- `anomaly_no_user`: the Stripe customer belongs to no Kairos user and the event carries no `userId` (for example a subscription created by hand in the dashboard). Either set `metadata.userId` on the subscription and resend, or, if it is not a Kairos customer, leave it: Stripe stops retrying after 3 days.
