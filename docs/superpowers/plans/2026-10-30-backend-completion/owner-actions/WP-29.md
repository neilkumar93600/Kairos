# WP-29 owner actions: submission attempts, settlement and extension leases

Nothing here blocks merging the code. Steps 1 and 2 belong to its deploy; step 3 is what proves it.

## 1. Deploy in this order (required)

The applier stops touching tables and calls the functions of migration `0027_wp29_attempt_functions`. Those functions and the narrowed grants need `ops/provision-roles.sql` run after the migration, and the running applier cannot do both at once. A send during the switch is safe either way (a claim that gets `permission denied` fails its job and retries; nothing has been sent), but with a slow switch the retries can run out and the row goes to `/api/admin/outbox` as dead.

1. Set the flag `pause_cloud_apply` to true (`/api/admin/flags`). The applier parks jobs; approvals are refused with `cloud_paused`.
2. Let the migration run, as for any release.
3. Run `ops/provision-roles.sql` (`owner-actions/WP-12.md`). After it the old applier cannot claim, and the new one can.
4. Deploy the release: api, worker, applier.
5. Set `pause_cloud_apply` back to false.

If the cloud channel is still closed to everyone but you, steps 1 and 5 can go: nothing is being sent.

## 2. Add Sentry alerts (recommended)

Page on `signal: submission_dual_detected`. Email on `signal: submission_report_anomaly`. What each means and what to do is in `docs/runbook/incident.md`.

## 3. Run the chaos test (required before the cloud channel opens beyond you)

GitHub > Actions > Chaos > Run workflow. It is the WP-22 harness, extended: it now also fails on a charge nobody reported, and it needs 50 applier kills with an attempt open. Default 1,000 approvals. If the verdict says fewer than 50 crashes, raise `CHAOS_APPROVALS` and run it again: that is a run that finished too soon, not a failed send.

**It has never run**, and neither have the integration tests of this package: the build machine has no Postgres, Redis or Docker. The first run may find bugs in the harness as well as in the code.

## Inputs with safe defaults

| Input | Default | Effect while unset |
|---|---|---|
| `LINK_SIGNING_KEY` (already on the WP-44 list) | none | A resend email goes without its link. The notification still shows. Set it before you rely on emailed resends |
| S-AP2 (proof that the apply POST can be intercepted per ATS) | not run | A run that dies while filling reads as `unconfirmed`, so the user gets "check your email first" and no automatic resend. Safe, and it is more cautious than the spec's post-S-AP2 table |

## One thing to know

The frozen extension does not call `/api/extension/claim`, so two tabs of the frozen extension sharing one session can still both send. The server records one charge and raises `submission_report_anomaly`. The claim closes this once the next extension release calls it (`frontend-handoff/WP-29.md`).
