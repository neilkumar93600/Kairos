# WP-17 owner actions: resume imports and the resume library

The code is on branch `wp/17`. Four things need you: two decisions the plan left open (import limits, the over-limit rule), the data key that is now required in production, and one storage rule.

## 1. DATA_KEKS is required in production (before deploying)

Imported resume text is stored only encrypted (`resume_imports.source_text_enc`, AES-256-GCM, `lib/crypto.ts`). A production api or worker without `DATA_KEKS` now refuses to boot. If it is not set yet, follow `docs/runbook/keys.md` (generate `v1:<base64 of 32 random bytes>`, store it in the password manager, set it on `sd1-api` and `sd1-worker` only, never on the applier). `.railway/railway.ts` already declares the variable.

After the first deploy the worker's hourly `backfill-sources` task moves every old plaintext resume (`resume_profiles.source_text`) into an encrypted import and empties the plaintext. Check it finished: `select count(*) from resume_profiles where source_text <> ''` returns 0 (about an hour after deploy; 100 profiles a run).

## 2. Import limits (decide, or keep the defaults)

Conservative defaults ship. Each is a service variable on `sd1-api`; no redeploy of code is needed to change one.

| Variable | Default | What it bounds |
|---|---|---|
| `IMPORT_MAX_PAGES` | 10 | Pages of an uploaded PDF read for text, LinkedIn profile exports included (a long LinkedIn export with many recommendations runs 5 to 8). Later pages are ignored. Range 1 to 30. |
| `IMPORT_MAX_CHARS` | 40,000 | Characters kept from one file, cut at a line break. Pasted text keeps the contract's 60,000. |
| `IMPORT_DAILY_LIMIT` | 20 | Imports (files and pasted text) per user per 24 hours, on top of the fixed `upload` rate class of 10 an hour. |
| `IMPORT_OVER_SLOT_LIMIT` | `refuse` | See section 3. |

Fixed in code (CISO mustFix 8, not owner choices): 5 MB per file, PDF and DOCX by magic bytes only, extraction in a worker thread with a 128 MB heap and a 20 second kill, two threads per api replica (a third concurrent upload answers 503 "try again"), DOCX zip limits (300 entries, 50 MB declared, ratio 100, 8 MB per part read), no macros, no DTDs.

LinkedIn PDF exports are detected from their text (profile link plus "Top Skills" or LinkedIn's page footer) and stored as `linkedin_pdf`; the same limits apply. If you want LinkedIn exports to count separately or have their own page cap, say so.

## 3. The over-slot-limit rule (decide)

Imports go into an existing resume profile (D8), so an import never creates a slot. The open case is a user who has more resume profiles than their plan now allows (after a downgrade). Default `refuse`: such a user can import into their first N profiles (default first, then oldest; N is the plan's `resumeProfiles`) and gets 403 for the others, so a downgrade cannot keep feeding the extra tracks. `allow` lets them import into any profile they still have. Their existing profiles and resumes are never deleted either way.

## 4. Uploads bucket: delete originals after 30 days

`06-infrastructure` and resume-57 keep an uploaded file 30 days. WP-17 stores the original under `uploads/<userId>/<importId>.pdf|docx` and keeps the extracted text (encrypted) in the database, so the file itself is never read again by the code. Simplest correct retention is a bucket rule rather than code: R2 > `kairos-uploads-staging` (and production) > Settings > Object lifecycle rules > Add rule: name `uploads-30d`, no prefix, delete objects 30 days after upload. This replaces the "per object, in code" line of `owner-actions/WP-14.md` section 3. Without the uploads bucket configured, imports still work and keep no original.

## 5. Migration 0011 ships one release later, and what it means for a rollback

`0011_drop_resumes_user_uq` drops the one-resume-per-user index. It is a contract change: the api before WP-17 upserts on that index, so once it is gone the old api answers 500 on GET and PUT `/api/resume`. Ship it in the release after the one that carries WP-17's code, once the new api is live everywhere (the coordinator holds the file back at merge). Until it runs, users keep one resume: creating a second base or a tailored copy answers 503 "A second resume opens with the next Kairos update", and a pipeline draft gets no saved copy (the draft itself is unaffected).

After 0011 has run, **rolling the api code back past WP-17 breaks `/api/resume`** until the index is rebuilt, and rebuilding it fails for any user who by then has two resumes. Roll forward instead. Rolling back the WP-17 code before 0011 runs is safe.
