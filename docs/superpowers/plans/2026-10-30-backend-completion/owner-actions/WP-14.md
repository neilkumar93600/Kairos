# WP-14 owner actions: Cloudflare R2 buckets, tokens and lifecycle rules

The code is on branch `wp/14`. Nothing in it needs R2 to deploy: with no `R2_*` variable set, the api and worker boot as today and any storage call answers `503 storage_unavailable`. Nothing writes files yet. Imports (WP-17), rendered PDFs (WP-19), sent snapshots (WP-29), the money journal (WP-13) and erasure (WP-25) start using the buckets when they land. Do these steps before the first of those packages ships. Steps 1 to 4 are for staging (`sd1-*`). Repeat them for production when WP-15 creates that environment, with the names in step 1 and no `-staging` suffix.

What the code does with them: four private buckets, each reached with its own token, so a leaked key opens one bucket. Every object key starts with the owner's user id, and `GET /api/files/...` serves only the caller's own keys. The applier never holds an R2 token. It gets presigned GET links of at most 5 minutes, and a production applier refuses to boot if any `R2_*_ACCESS_KEY_ID` or `R2_*_SECRET_ACCESS_KEY` is set on it.

## 1. Create four buckets

Cloudflare dashboard (signed in with your hardware key) > R2 Object Storage > Create bucket, four times. Location: Automatic, with the location hint **Eastern North America** (next to Railway US East). Default storage class.

| Bucket (staging) | Production | Holds |
|---|---|---|
| `kairos-uploads-staging` | `kairos-uploads` | Resume files users import (WP-17) |
| `kairos-renders-staging` | `kairos-renders` | Rendered PDFs and the render cache (WP-19) |
| `kairos-snapshots-staging` | `kairos-snapshots` | The exact PDF sent with each application (WP-29), kept for the receipt |
| `kairos-backups-staging` | `kairos-backups` | Encrypted dumps and the money journal (WP-13) |

`06-infrastructure.md` 4.3 also lists `kairos-failures` (applier failure snapshots) and `kairos-tombstones` (deletion tombstones). Create those with the packages that write them (WP-29, WP-25), not now.

Then, for each bucket, open Settings and check:

- **Public Development URL (r2.dev): Disabled.** This is the default. Never enable it.
- **Custom Domains: none.** Never connect one. A custom domain makes the bucket public.
- **CORS policy: none.** The web downloads through the api (same origin, through the `/api` rewrite), and the applier fetches its links from Node, not from the employer's page. If WP-19 later gives the Chrome extension a presigned link, that package adds a GET-only rule on the snapshots bucket for the five ATS origins.

This covers the WP-14 acceptance item "no public bucket exists". Write down that you checked it, with the date.

## 2. Lifecycle rules

Bucket > Settings > Object lifecycle rules > Add rule.

| Bucket | Rule |
|---|---|
| renders | Name `renders-30d`, no prefix (whole bucket), delete objects 30 days after upload. A missing render is re-rendered from the database. |
| snapshots | None. Snapshots stay until erasure (WP-25) deletes the user's prefix. The receipt must keep showing exactly what was sent. |
| uploads | None. The "originals removed 30 days after a successful parse" rule is per object and runs in code (WP-17, WP-25). |
| backups | Three rules by prefix: `core/` delete after 7 days, `full/` after 28 days, `journal/` after 35 days (06-infrastructure 5.3). They match nothing until WP-13 writes there, so you can set them now. |

Keep the default rule that aborts incomplete multipart uploads after 7 days on every bucket.

Versioning: `06-infrastructure.md` asks for versioning on uploads and backups. If the bucket settings show no versioning option (R2 had none when this was written), skip it. A deleted upload is recovered by the user uploading it again, and backups are covered by WP-13's retention and bucket lock decision.

## 3. Create seven API tokens (one per bucket and service)

R2 Object Storage > Manage API tokens > Create **Account API token**, seven times. For each one: choose the permission below, select **Apply to specific buckets only** with exactly one bucket, set no TTL and no IP filter, and name it as shown. After creating it, Cloudflare shows the Access Key ID and the Secret Access Key once. Put both in your password manager under the token's name, then go straight to step 4.

| Token name (staging) | Bucket | Permission | Service |
|---|---|---|---|
| `kairos-staging-api-uploads` | uploads | Object Read & Write | `sd1-api` |
| `kairos-staging-api-renders` | renders | Object Read & Write | `sd1-api` |
| `kairos-staging-api-snapshots` | snapshots | **Object Read only** | `sd1-api` |
| `kairos-staging-worker-uploads` | uploads | Object Read & Write | `sd1-worker` |
| `kairos-staging-worker-renders` | renders | Object Read & Write | `sd1-worker` |
| `kairos-staging-worker-snapshots` | snapshots | Object Read & Write | `sd1-worker` |
| `kairos-staging-worker-backups` | backups | Object Read & Write | `sd1-worker` |

The api never gets a backups token: dumps hold every user's data. The applier gets no token at all. Never use an Admin permission or an "all buckets" token, and never store the account owner's own API token in any service (06-infrastructure 4.5).

## 4. Railway variables

The endpoint is the same for every token: `https://<account id>.r2.cloudflarestorage.com`. The account id is on the R2 overview page, and the token page shows the full URL.

| Variable | `sd1-api` | `sd1-worker` |
|---|---|---|
| `R2_ENDPOINT` | the endpoint | the endpoint |
| `R2_BUCKET_UPLOADS` | `kairos-uploads-staging` | `kairos-uploads-staging` |
| `R2_UPLOADS_ACCESS_KEY_ID`, `R2_UPLOADS_SECRET_ACCESS_KEY` | `kairos-staging-api-uploads` | `kairos-staging-worker-uploads` |
| `R2_BUCKET_RENDERS` | `kairos-renders-staging` | `kairos-renders-staging` |
| `R2_RENDERS_ACCESS_KEY_ID`, `R2_RENDERS_SECRET_ACCESS_KEY` | `kairos-staging-api-renders` | `kairos-staging-worker-renders` |
| `R2_BUCKET_SNAPSHOTS` | `kairos-snapshots-staging` | `kairos-snapshots-staging` |
| `R2_SNAPSHOTS_ACCESS_KEY_ID`, `R2_SNAPSHOTS_SECRET_ACCESS_KEY` | `kairos-staging-api-snapshots` | `kairos-staging-worker-snapshots` |
| `R2_BUCKET_BACKUPS`, `R2_BACKUPS_ACCESS_KEY_ID`, `R2_BACKUPS_SECRET_ACCESS_KEY` | **not set** | `kairos-staging-worker-backups` |

Set each value as a plain variable on that one service, not as a shared variable: the two services hold different keys for the same bucket. Set nothing `R2_*` on `sd1-applier`.

A bucket's three variables go together. If one is missing, the deploy log shows for example `R2_SNAPSHOTS_SECRET_ACCESS_KEY: required with R2_BUCKET_SNAPSHOTS` (names only, never values) and the service restarts in a loop. Fix the variable and redeploy. A production `R2_ENDPOINT` must be https.

## 5. Check it: `r2:smoke` (about 30 seconds per service)

From the repository root on branch `wp/14`, with the Railway CLI signed in to the project. Run the api first, then the worker, whose last check also deletes the api's probe files:

```
railway run --service sd1-api -- npm run r2:smoke -w @auto-career/server -- api
railway run --service sd1-worker -- npm run r2:smoke -w @auto-career/server -- worker
```

Each line starts with `ok` or `FAIL`, and the run ends with `all R2 checks passed for the api` (or `worker`) and exit code 0. It checks, per bucket: write and read with that service's token, matching the table in step 3; that another bucket's token is refused (proving the tokens are bucket-scoped, spike S-INF1); and for renders and snapshots, that a presigned GET works and answers 403 once it has expired. The worker run also checks that erasure empties a prefix. It writes small probe files under the user id `r2-smoke` and deletes them again. The backups probe stays under `journal/` until the 35-day rule removes it.

What a `FAIL` usually means:

- `write no (AccessDenied), expected yes`: the token has Read only, or is scoped to another bucket. Recreate it (step 3).
- `snapshots: write yes, expected no` on the api: the api's snapshots token is Read & Write. Recreate it as Object Read only.
- `the renders token is refused: yes`: two buckets share one token. Create one token per bucket.
- `backups: configured (expected no token)` on the api: delete the three backups variables from `sd1-api`.
- `expired presigned GET answers 200`: your machine's clock is more than 4 seconds behind. Sync it and rerun.

Send me the output of both runs. It contains no keys or personal data.

## 6. Rotation

Yearly, and at once if a key may have leaked (06-infrastructure 4.6): create the replacement token for that bucket and service, update the two variables on that service, redeploy it, run `r2:smoke` for it, then delete the old token in Cloudflare. A leaked key affects one bucket, so rotate only that token.

## What this package does not cover, and where it differs from the specs

- **Presigned links.** `06-infrastructure.md` 4.3 says no presigned URL is ever issued. WP-14 issues them for the applier only: renders and snapshots only, at most 300 seconds, minted by a process that holds the token (the worker, in WP-19). The web never gets one. It downloads through `GET /api/files/...`.
- **Buckets.** The spec lists five buckets (uploads, renders, failures, backups, tombstones). This package adds snapshots, because the sent snapshot must not inherit the renders' 30-day rule (02-database 7.3.1 amendment), and leaves failures and tombstones to WP-29 and WP-25.
- **Variable names.** `06-infrastructure.md` 4.2 names one key pair (`R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`). One token per bucket needs one pair per bucket: `R2_<BUCKET>_ACCESS_KEY_ID` and `R2_<BUCKET>_SECRET_ACCESS_KEY`.
- **The api's forbidden backups token** (06-infrastructure 4.4) is not enforced at boot, because the api and the worker share one environment schema. Step 4 and the `r2:smoke api` check cover it.
- Encrypting uploads in the application (06-infrastructure 7.2 TB10 and 8.3, `DATA_KEKS`) is WP-17 with WP-18's library. R2 encrypts every object at rest regardless.
