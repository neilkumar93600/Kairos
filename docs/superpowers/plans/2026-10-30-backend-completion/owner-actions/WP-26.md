# WP-26 owner actions: the claim verifier

Nothing here blocks the merge. Every path ships in `shadow`: verdicts are counted, nothing is dropped.

## Before the 7-day shadow counts

1. **Confirm `LLM_GATEWAY=anthropic` on the api and worker.** The verifier is a gateway agent. On the legacy client no verification runs (the counter `verifier.skipped_legacy` rises), so a shadow week on legacy measures nothing. Setting a path to `enforce` on legacy makes that route answer 503.
2. **Run the eval live, once it is approved to spend.** `ALLOW_LLM_NETWORK=1 ANTHROPIC_KEY_EVALS=... npm run eval -- --live --repeat 3 --agent claim-verifier --agent claim-verifier-escalation`. The committed fixtures hold the gold labels, so they prove the plumbing and nothing about the model. The bars (false accept at most 1%, false reject at most 8%) mean something only in this run. No live run has been made.
3. **Label the full set.** The starter set is 42 verifier claims and 12 escalation claims, all synthetic and labelled by the builder. A 1% bar needs far more: agents/08 9 asks for 400 claims, 200 of them `self_preference` written by the production drafters on eval personas and labelled by the owner. At 42 claims one miss is already over the bar. Add cases to `server/evals/claim-verifier/cases.jsonl`, then record them with `npm run llm:record`.

## After 7 days

Review `verifier.verdicts` in `metrics_minute` daily (label `path:verdict:mode`), plus `verifier.unavailable`, `verifier.escalation_capped` and `verifier.steering`. Once the live bars pass, flip one path at a time, from an admin session with a fresh sign-in:

```
PUT /api/admin/flags/verifier_mode:suggestions  {"value":"enforce"}
PUT /api/admin/flags/verifier_mode:tailor       {"value":"enforce"}
PUT /api/admin/flags/verifier_mode:drafts       {"value":"enforce"}
```

It takes effect within 10 seconds. Setting `"shadow"` undoes it. `prepare` and `patch` are WP-41's to flip. Production text is not stored on these routes, so production false-accept and false-reject rates cannot be measured from them, only verdict counts.

## Levers (all audited, 10 seconds, no deploy)

| Key | Value | Effect |
|---|---|---|
| `agent_disabled:claim-verifier` | `true` | Calls fail: shadow carries on unverified, enforce answers 503 |
| `prompt_pin:<agent>` | version number | Runs that version |
| `model_pin:<agent>` | `claude-haiku-5-5` or `claude-sonnet-5-5` | Replaces the primary model. A pin to Sonnet costs that much more per call |
| `prompt_canary:<agent>` | `{"version":2,"percent":10}` | Drafting agents only. Ignored for the verifiers |
| `prompt_shadow:<agent>` | `{"version":2,"percent":5}` | At most 5%. Runs under the `ops` budget. For a verifier, only agreement counts are kept |

## Alerts

`verifier_escalation_high` fires when escalations pass 10% of the day's verifier calls, with at least 100 verifier calls. It reaches Sentry, not email: the spec's "email at 10%" is not built. At 15% claims are dropped as unverified.
