# WP-03 owner actions: the edge secret and shared rate limits

The code is on branch `wp/03`. Do steps 1 to 3 before deploying `wp/03` to `sd1-api`: from this package on, a production api refuses to boot without `KAIROS_EDGE_SECRET` ("KAIROS_EDGE_SECRET: required on the api in production").

What changes for you: the api now tells browsers apart. Until now every web user reached the api from Vercel's address, so they shared one rate-limit bucket, and Better Auth put the whole site in one bucket of 3 sign-ins per 10 seconds. From this package on, the web edge proves itself with a secret header, and the api uses the browser's own address only when that secret matches. Limits are kept in Postgres, so they hold across api replicas and deploys.

## 1. Create the secret

Generate 32 random bytes on your machine and keep the output out of chat, tickets and commits:

```
node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"
```

The api refuses a value shorter than 32 characters. Rotate it like `LINK_SIGNING_KEY`: set the new value in both places (steps 2 and 3), then redeploy both. Between the two redeploys, browser traffic is keyed on Vercel's address as before (no outage, only shared limits for a few minutes).

## 2. Vercel, project `kairos` (web/)

| Variable | Value |
|---|---|
| `KAIROS_EDGE_SECRET` | The value from step 1, for Production and for Preview. A plain server variable: never prefix it with `NEXT_PUBLIC_`, which would ship it to every browser. |

Vercel applies variable changes to new deployments only, so redeploy the web after setting it. Preview deployments that point at the staging api need the same value as that api.

## 3. Railway, service `sd1-api` only (staging, and the production api when it exists)

| Variable | Value |
|---|---|
| `KAIROS_EDGE_SECRET` | The same value as on Vercel. |
| `TRUSTED_PROXY_HOPS_DIRECT` | Leave unset (it defaults to 0). Change it only after step 5 shows an internal address. |

Do not set either on the worker or the applier; they do not read it, and the applier should hold as few secrets as possible (CISO mustFix 1).

Migration `0003_rate_limits` (two new unlogged tables, `rate_limits` and `auth_rate_limit`) runs by itself in the api's pre-deploy step. Unlogged tables are emptied by a database crash and skipped by backups; that only resets the limit windows.

## 4. Deploy order

Any order works once both variables are set. An api with the secret simply ignores a web without it (limits fall back to Vercel's address, as today) until the web is redeployed.

## 5. Check the real header chain on staging (spike S-B1)

1. Through Vercel: run the WP-02 smoke test against the Vercel domain (`SMOKE_BASE_URL=https://<vercel domain> SMOKE_EMAIL=<you> node scripts/smoke.mjs`). In the `sd1-api` logs, find a request line by its probe id. `x-kairos-client-ip` must be your public address (compare with https://ifconfig.me), and there must be no `x-kairos-edge` header in the line.
2. Straight to Railway, with forged headers:
   ```
   curl -s -H "x-vercel-id: fra1::forged" -H "x-forwarded-for: 1.2.3.4" -H "x-kairos-client-ip: 5.6.7.8" -H "x-kairos-edge: guess" https://<railway api domain>/api/auth-providers
   ```
   In the log line for that request, `x-kairos-client-ip` must again be your own public address, never `1.2.3.4` or `5.6.7.8`.
3. If in check 2 the address is a private one (`10.x`, `100.64.x` to `100.127.x`, `172.16.x` to `172.31.x`, `192.168.x`) instead of yours, Railway has an internal proxy after its edge: set `TRUSTED_PROXY_HOPS_DIRECT=1` on `sd1-api`, redeploy and repeat check 2. Never raise it otherwise: one hop too many lets a caller choose its own address again.

Record both results (date, deploy id, the addresses seen) in the WP-03 acceptance notes.

## 6. Check that limits survive two replicas and a redeploy (acceptance)

1. In Railway, set `sd1-api` to 2 replicas.
2. Send 6 empty contact posts in a row (an empty body fails validation, so nothing is stored or mailed):
   ```
   for i in 1 2 3 4 5 6; do curl -s -o /dev/null -w "%{http_code}\n" -X POST -H "content-type: application/json" -d "{}" https://<vercel domain>/api/contact; done
   ```
   Expected: `422` five times, then `429`. The posts are spread over both replicas, so a `429` on the sixth proves the count is shared.
3. Redeploy `sd1-api` and send one more: still `429` (the contact window is one hour).
4. Set the replicas back if you do not want two.

## 7. Clearing a limit by hand (for repeated smoke runs)

Sign-up is capped at 3 attempts per address per day, and the smoke test signs up once per run. To clear your own counters on staging:

```
DELETE FROM auth_rate_limit WHERE key LIKE '%|/sign-up/email';   -- per-address auth limits, key is '<ip>|<path>'
DELETE FROM rate_limits WHERE key LIKE 'auth_%';                  -- per-email sign-in and code limits (hashed emails)
```

## 8. Decision needed: the sign-up cap on shared networks

The spec's cap (05-api 6.4, D-25) is 3 sign-up attempts per address per day, against free-credit farming. It counts attempts, not accounts created, and one campus, hostel or mobile-carrier network (CGNAT) often puts many students behind one IPv4 address, so the whole network gets 3 sign-ups a day. The same applies, less sharply, to code mails (10 per address per hour). Reply with one of:

- keep 3 per day (as built);
- raise it (for example 20 per day), a one-line change in `server/src/lib/auth.ts`;
- count only accounts actually created, a small code change in a later package.
