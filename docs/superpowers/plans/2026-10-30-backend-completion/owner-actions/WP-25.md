# WP-25 owner actions: erasure, retention, scrubs, export

The code is on branch `wp/25`. What it adds:

- **Erasure.** Settings > Delete account cancels Stripe (as before), then deletes every row of the account in one transaction: it records a `deletion_tasks` row, keeps the credit ledger in `credit_ledger_archive` under a keyed hash of the user id, stores a keyed hash of the normalized address in `erased_emails`, deletes the user's contact messages and the user row with its cascade. Within a minute the worker writes the R2 tombstone, deletes the Stripe customer, checks that no table holds the user id, empties the user's R2 prefixes and nulls their `llm_calls` hash. A task still open after 24 hours raises `erasure_overdue` in Sentry. A daily job deletes R2 prefixes that belong to no user (`orphan_uploads`).
- **No second free grant.** A new account whose normalized address (case, dots for Gmail, `+tag`) belongs to an erased account gets no free credits.
- **Retention**, daily: reply bodies emptied after 180 days, contact messages deleted after 12 months, below-bar matches after 30 days, closed jobs after 180 days (deleted, or their description purged when an application points at them). **Scrub**, daily: sensitive answer and receipt values (EEO, visa, salary, personal ids) blanked 7 days after an application is submitted or withdrawn. Receipts no longer store addresses or phone numbers from the employer's confirmation page.
- **Consent.** Every sign-up records the terms and privacy notice version (`consent_records`).
- **Operator scripts.** `scripts/export-user.ts` (access request), `scripts/erase-user.ts` (an erasure request by email), `scripts/replay-tombstones.ts` (after a restore; now step 5b of R-DR-1 and step 4.4 of R-DR-2).

Deploying `wp/25` is safe before steps 1 to 3, with one exception: production now refuses to boot without `USER_HASH_KEY` (step 2). Until the tombstones bucket exists (step 1), every production erasure stays open with `tombstones_unconfigured` and pages after 24 hours, though the account itself is deleted at once.

## 1. The tombstones bucket (15 minutes per environment)

As owner-actions/WP-14.md steps 1 to 4, for one more bucket:

| Bucket (staging) | Production | Holds |
|---|---|---|
| `kairos-tombstones-staging` | `kairos-tombstones` | One JSON object per erased account: two keyed hashes and a time, no id or address |

- Lifecycle rules: **none**. Tombstones are kept forever (06-infrastructure X15): a tombstone must outlive every backup that could bring the account back.
- Tokens: `kairos-staging-api-tombstones` (Object Read & Write) for `sd1-api`, `kairos-staging-worker-tombstones` (Object Read & Write) for `sd1-worker`. R2 has no write-only permission; the objects hold no personal data.
- Variables on `sd1-api` and `sd1-worker`: `R2_BUCKET_TOMBSTONES`, `R2_TOMBSTONES_ACCESS_KEY_ID`, `R2_TOMBSTONES_SECRET_ACCESS_KEY`. Never on the applier.
- If R2 offers bucket lock or retention lock, turn it on for this bucket [verify S-INF1].

## 2. `USER_HASH_KEY` (5 minutes)

Production refuses to boot without it. If the api and the worker already have it (it was required with `LLM_GATEWAY=anthropic`), nothing to do. Otherwise set the same value on both: `openssl rand -base64 32`, kept in the password manager and the emergency kit (docs/runbook/keys.md).

**Never rotate it, and guard it like a signing key** (docs/runbook/keys.md section 10). It keys the deletion tasks, the ledger archive, the erased-address list, every tombstone, the audit pseudonyms and `llm_calls`. A new key makes tombstone replay miss every account erased before the change and lets those addresses take a second free grant; a leaked key lets anyone reverse those hashes with a list of ids or addresses.

## 3. Roles (5 minutes, after the migration)

Run `ops/provision-roles.sql` again (as in owner-actions/WP-12.md): it grants the api and the worker the four new tables, and the api `DELETE` on `contact_messages` for the erasure.

Ask counsel to confirm or change each item for DPDP Act 2023 and GDPR, then put the decided values in the privacy notice.

## 5. Handling requests (each time)

- **Access or portability:** confirm the requester owns the account (they write from its address, or sign in and use the contact form), then `railway run --service worker -- npx tsx scripts/export-user.ts <userId> --out ./export-<userId>`. Send `export.json` and the `files/` folder over an agreed channel and delete your copy. Note the request, date and delivery in your request log.
- **Erasure without a sign-in:** confirm ownership the same way, then run `railway run --service worker -- npx tsx scripts/erase-user.ts <userId>`: it prints the account's email and creation date. Check that it is the requester, then re-run with `--apply --confirm <that email>`. Also use this for an account whose Settings deletion keeps failing (a very large account can exceed the request's 10-second limit; the account then stays whole).
- **Copies outside the database:** the contact form also mails each message to `CONTACT_ALERT_TO` (WP-44). When an erasure request names a sender, delete their messages from that mailbox too.
- **An `erasure_overdue` alert:** `select user_hash, last_error_code, attempts from deletion_tasks where completed_at is null;` The code names the store: `tombstones_unconfigured` and `storage_unconfigured` (a bucket variable missing on the worker), `stripe_unconfigured`, `rows_remain` (a table the cascade does not reach: a bug, tell the developer), `audit_pseudonymise_failed` (the worker lacks `UPDATE (actor)` on `ops_audit`, or the audit trigger refused; re-run `ops/provision-roles.sql`), `step_failed` (Stripe or R2 errors; see the worker log). An `orphan_uploads` signal means the daily job deleted R2 prefixes of no user; a worker log line "prefixes that are not user ids" means something wrote outside the per-user layout and was left alone.

## 6. The erasure drill (WP-25 acceptance, before launch, then with each restore drill)

On staging, with steps 1 to 3 done:

1. Create a test account, upload a resume, approve an application, send a contact message from its address. Note its user id.
2. Delete it from Settings. Within 5 minutes, `select * from deletion_tasks order by requested_at desc limit 1;` shows `completed_at` set. The tombstone object exists in `kairos-tombstones-staging`; the user's prefixes in the uploads, renders and snapshots buckets are empty.
3. Sign up again with the same address (try it with capital letters): the account works and shows 0 free credits.
4. As part of the R-DR-1 drill, restore to a point before step 2 and run step 5b: the account cannot sign in on the sibling, and `deletion_tasks` shows it again with `requested_by = 'replay'`.

Pass: all of the above within 24 hours. Record the date in R-DR-1's drill table.
