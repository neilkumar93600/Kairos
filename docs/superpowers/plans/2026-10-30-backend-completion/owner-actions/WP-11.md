# WP-11 owner actions: detection and the incident runbook

The code is on branch `wp/11`. Once deployed, the api, worker and applier send errors to Sentry, scrubbed in the process. The worker and the applier serve an internal `GET /health` and ping a heartbeat URL every minute while healthy. `GET /health` and `GET /api/health` answer status only. A SIGTERM drains in-flight work before the process exits: 25 s for the api, 30 s for the worker, 170 s for the applier.

None of that alerts anyone until the steps below are done. With no `SENTRY_DSN` and no `HEARTBEAT_URL`, the code does nothing new, so `wp/11` is safe to deploy first.

Railway cannot alert on the content of log lines; it alerts only on CPU, RAM, disk and egress, plus deploy events. So the five CISO detections (5xx rate, auth 429 spikes, inbound 401/403 bursts, applier allowlist refusals, `admin_adjustment` ledger rows) arrive as Sentry events, and the Sentry alert rules in step 5 replace the "Railway log alerts" of the plan.

## 2. Sentry

1. Create an organization, then two projects, both platform Node.js:
   - `kairos-server`, for the api and the worker (events carry the tag `service:api` or `service:worker`);
   - `kairos-applier`.

   The applier gets its own project because it runs hostile employer pages: if one ever takes over the process, it can read that DSN and flood or forge events. A separate project keeps that away from the server's issues and quota. The applier sends only error types, our own stack frames and signal counts; it never sends a message, a URL or anything a page wrote (`server/src/lib/sentry.ts`).
2. Data region: US, beside Railway US East. Add Sentry to the privacy notice's sub-processors. By design it receives a hashed user id, request ids, error types and stack frames, and no personal data.
3. In each project, open Settings > Security & Privacy and turn on **Data Scrubber**, **Use Default Scrubbers** and **Prevent Storing of IP Addresses**. Add `email`, `text`, `answers`, `coverLetter`, `cookie` and `token` as additional sensitive fields. The code already strips all of these; this is the second lock.
4. Rate limits, under Settings > Client Keys (DSN) > Configure > Rate limit: 60 events per hour on `kairos-applier`, 600 per hour on `kairos-server`. Keep Spike Protection on. In Organization > Subscription, set the pay-as-you-go budget to USD 50.
5. Copy each project's DSN.

Neither key is a secret. The applier's env check accepts both, and `test/env.roles.test.ts` pins that. Railway sets `RAILWAY_GIT_COMMIT_SHA`, which becomes the Sentry release, and `RAILWAY_ENVIRONMENT_NAME`, which becomes the Sentry environment; you set neither. On a service that deploys from an image rather than from GitHub, the release is simply missing.

The health and draining settings are in `server/railway/{api,worker,applier}.json`:
- healthchecks of 60, 120 and 120 s;
- `drainingSeconds` of 60, 60 and 180;
- `overlapSeconds` of 20 on the api.

Check each service: Settings > Config-as-code must point at its file. Otherwise, set the same values in the dashboard. After the next deploy, the worker and applier deployments show the healthcheck passing.

## 4. The uptime vendor

1. Two HTTP monitors, each every minute from at least two regions. Each expects status 200 and a body containing `"status":"ok"`, and pages after 3 minutes failing (A-AVAIL-1):
   - `https://<api domain>/health`: the API directly;
   - `https://<web domain>/api/health`: the same handler through the Vercel rewrite.
2. Two heartbeat monitors, `worker` and `applier`: a period of 1 minute and a grace of 3 minutes, so a stopped process pages within 5 minutes (A-AVAIL-3). Copy their ping URLs into step 3.
3. A status page at `status.<domain>` with the components Web, API, Cloud applier and Email.
4. Note the vendor's inbound email address (or webhook) for creating incidents; step 5 sends Sentry's page-level alerts there.

## 5. Sentry alert rules

Use Alerts > Create Alert [verify the labels in your Sentry version]. Set "page" actions to email the vendor's incident address and "email" actions to email you. On every rule, set the action interval to 30 minutes.

| Project | Rule | Condition | Action |
|---|---|---|---|
| `kairos-server` | 5xx rate (metric alert, on number of errors) | Filter `service:api level:error`: critical above 10 in 5 minutes, warning above 3 | Critical: page. Warning: email |
| `kairos-server` | New error (issue alert) | A new issue is created, or an issue regresses; level is `error` | Email |
| `kairos-server` | Security signal, page | A new issue is created, or an issue regresses, or the issue is seen more than 5 times in 1 hour; tag `signal` equals `admin_adjustment_row` | Page |
| `kairos-server` | Security signal, email | The same triggers; tag `signal` equals `auth_rate_limited` or `inbound_token_rejected` | Email |
| `kairos-applier` | Security signal, page | The same triggers; tag `signal` equals `applier_internal_blocked` | Page |
| `kairos-applier` | Signals and errors | The same triggers; tag `signal` equals `applier_nav_blocked`, or level is `error` | Email |

A signal is one Sentry issue per signal name. **After handling one, resolve the issue**, so the next occurrence alerts again as a regression. What each signal means, and what to do about it, is in `docs/runbook/incident.md` ("Security signals"). The per-minute bars are in `SIGNALS` in `server/src/lib/sentry.ts`. If one is noisy after two weeks, tell me the count and I will change the bar.

## 7. Acceptance drills (staging, about 30 minutes)

Run these once steps 2 to 6 are in place. Write the times in the WP-11 acceptance notes.

1. **A forced 500 reaches Sentry with no personal data.** Stop the Postgres service on `sd1` (this also rehearses R-PG-1). Then send:

   ```bash
   curl -s -X POST https://<api domain>/api/contact -H 'content-type: application/json' \
     -d '{"name":"Drill Marker","email":"drill-marker@example.com","topic":"other","message":"wp11 drill marker text"}'
   ```

   After the driver's connect timeout (up to about 20 seconds), it answers `500 {"error":{"code":"internal",...,"requestId":"..."}}`. Within a minute, `kairos-server` has an `unhandled error` issue tagged `service:api`, `path:/api/contact`, and that `requestId`. Open the event's JSON and search it for `Drill`, `drill-marker`, `marker text` and `example.com`: none may appear. The message stops at `Failed query: insert into "contact_messages" ...`, before `params:`.
2. **Stopping the worker pages within 5 minutes.** Keep Postgres stopped for 4 minutes: both HTTP checks and both heartbeats page. Start Postgres again and confirm that all four recover. Then remove the `sd1-worker` deployment, note the time, and wait for the page; it should take 5 minutes or less. Redeploy the worker.
3. **A SIGTERM during a request lets it complete.** Run this loop while you redeploy `sd1-api`:

   ```bash
   for i in $(seq 1 600); do curl -s -o /dev/null -w "%{http_code}\n" https://<web domain>/api/health; sleep 0.2; done | sort | uniq -c
   ```

   Expect only `200`, plus a few `503`s while the old deployment drains. Any `502` or `000` means a dropped request: send me the output. The unit test `test/lifecycle.test.ts` covers the drain itself.
4. **The runbook.** Read `docs/runbook/incident.md` and the P1 runbooks beside it: R-HEALTH-1, R-HEALTH-2, R-PG-1, R-PG-4 and R-DEPLOY-1 to R-DEPLOY-3. Fill in what only you know: the deploy branch, your contact for counsel, and the support address. Reply "WP-11 runbook reviewed", and schedule the tabletop rehearsal of a leaked-secret incident before launch.
