# WP-35 owner actions: consent defaults, the postal address, the first broadcast

The code is on branch `wp/35`. It deploys without any of these and sends nothing: every account starts **opted out** of the four optional mail kinds (digest, weekly outcome report, Autopilot summary, reminders), and in production the digest tick holds back (claims nothing, loses nothing) until step 2 is done. Do steps 1 to 4 before the first digest.

## 1. Decide the consent default (counsel first)

| Variable | Services | Value |
|---|---|---|
| `MAIL_CONSENT_DEFAULT` | api, worker | The column default in the database is always opt-out (all four kinds); only `bootstrapUser` applies `opt_in`, so an account made any other way starts opted out. `opt_out` (default and safe): a new account gets no digest until the person turns it on in Settings, which records their consent (`consent_records`, purposes `mail_digest`, `mail_outcome_report`, `mail_autopilot_summary`, `mail_reminders`). `opt_in`: a new account starts with all four on and four consent rows are written at sign-up. Choose it only when counsel has approved the sign-up form's wording (the form must say that job digests and reminders are included, and the consent must be as easy to withdraw as to give; every digest carries a one-click unsubscribe). |

Existing accounts: migration 0022 opted **every existing profile out** of all four kinds, because nothing was ever sent and nobody consented. If counsel agrees that existing users may be opted in (for example because the terms they accepted say so), run once, after the migration:

```sql
update profiles set mail_opt_out = '{}' where created_at < now();
```

and, if you also want the matching consent rows, `insert into consent_records (user_id, purpose, version) select user_id, p, '<PRIVACY_NOTICE_VERSION>' from profiles, unnest(array['mail_digest','mail_outcome_report','mail_autopilot_summary','mail_reminders']) p on conflict do nothing`. An address that unsubscribed earlier is not lifted by this: new sign-ups stay opted out of what their address refused (step 5), but the SQL above does not look at `mail_opt_outs`, so exclude those yourself if any exist.

## 2. The sender's postal address (CAN-SPAM footer)

| Variable | Services | Value |
|---|---|---|
| `MAIL_POSTAL_ADDRESS` | api, worker | The address printed under every broadcast email, for example `Kairos Inc, 1 Main Street, Austin TX 78701, USA`. 10 to 300 characters. A street address, a PO box or a commercial mailbox registered with the post office all qualify. |

Unset in production: the digest tick logs `digests held back` with the missing names and claims nothing, and the send path refuses broadcast mail with an error. Also required for any broadcast: `LINK_SIGNING_KEY` and `API_PUBLIC_ORIGIN` (owner-actions/WP-44.md section 3).

## 3. Postmark broadcast stream: its unsubscribe management, and one test

Postmark's documentation says broadcast message streams require unsubscribe management, with `Postmark` as the default, and that approved accounts can use `Custom`; `None` is not offered on broadcast streams. So ask Postmark support to approve **`Custom`** for the broadcast stream (we send our own signed link and `List-Unsubscribe` headers). Under the default `Postmark` setting Postmark may add its own unsubscribe link and header to each message; the documentation I could read does not say what it adds or what it does to our `List-Unsubscribe` and `List-Unsubscribe-Post` headers. **That is unverified, so the test send below must check both.**

Create the broadcast stream (owner-actions/WP-44.md section 1), then send one digest to a test address you own (turn the digest on for a test account, make a match, and set that search's `next_digest_at` to the past). In the received message check, with "show original": which `List-Unsubscribe` and `List-Unsubscribe-Post` headers are present (ours, Postmark's, or both; there must be a working one-click header), whether the body has one footer link or two, that the footer shows the postal address, that the Unsubscribe button in Gmail or Apple Mail works, and in Postmark's activity page that the message went out on the broadcast stream. Then click Gmail's Unsubscribe: Postmark sends a `SubscriptionChange` event (`ManualSuppression`, with the stream) to the events webhook, which turns the optional mail off for that account without suppressing account mail. If our headers are replaced and the Postmark-managed path is the only one working, that still works through this event; tell the coordinator what you saw before the first real digest.

## 4. Roles

Run `ops/provision-roles.sql` again after migration 0022 has run (owner-actions/WP-12.md). It grants `saved_searches`, `reminders` and `mail_opt_outs`.

## 5. Privacy notice sentence (counsel item)

Opt-outs are kept after an account is erased, on purpose, like the suppression list: `mail_opt_outs` holds a keyed hash of the address and the kind of mail refused (no address, no user id), so a person who unsubscribed and signs up again with the same address stays opted out until they turn the mail on themselves. Add one sentence to the privacy notice next to the one for suppressed addresses. The hash key is `USER_HASH_KEY`, which must never rotate (docs/runbook/keys.md).

## Operating notes

- Digests run at minute 25 of each hour for searches due at 08:00 in the person's time zone; reminders are created at minute 50 and ride in the next digest. Nothing else to schedule.
- Looking for what happened to digests: `select kind, status, error_code, count(*) from email_sends where kind = 'digest' group by 1,2,3`. `unsubscribed` is a person who turned digests off after the tick; `empty` and `superseded` are normal.
- The contact form's founder alert goes to `CONTACT_ALERT_TO` through the notify queue. A message whose alert was lost (Redis down) is queued again within about 7 minutes.
