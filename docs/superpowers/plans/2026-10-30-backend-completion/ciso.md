## Threats (STRIDE)

- E, I: A hostile or compromised employer page takes over the applier container, which holds every secret and full access to the database (cloud-apply.ts:21,56,59; env.ts:10-23). Mitigation: mustFix 1: apply URLs built from token and id and checked against the host allowlist, navigation allowlist, secrets removed, applier DB role, Chromium sandbox or a signed acceptance, Chromium refreshed on each Playwright release; the P5 egress guard of 06-infrastructure 7.5.
- D: Unauthenticated large or gzip-inflated bodies block or exhaust the api (webhooks.ts:71-73; better-call node.cjs:4-11). Mitigation: mustFix 2: check the secret before parsing, inflate:false, a 64 KB cap on /api/auth, 16 KB stored bodies, a webhook limiter.
- D: Denial of wallet: scripted free accounts, user-imported boards and sign-up farming drive unbounded Sonnet and Haiku spend (resume.ts:26-33; jobs.ts:24-29; score-matches.ts:30-60). Mitigation: mustFix 3: Console spend cap, gateway envelopes, a userId on every call, aiDailyAllowance enforced in Postgres, no scoring of postings from imported boards, scoring limited to active users.
- D: Sign-in and sign-up locked for the whole site through the shared Better Auth bucket and the Vercel-egress key (auth.ts:69; ip.mjs:174-193; app.ts:22). Mitigation: mustFix 4: edge-secret client-IP header, user-id keys for signed-in traffic, database-backed limiter storage, per-email limits.
- S: Client-IP spoofing that evades IP-keyed auth and sign-up limits through direct calls to the public Railway API (05-api.md:471-480). Mitigation: Trust only an authenticated edge header; otherwise use the rightmost hop; amend the spec and test with forged x-vercel-id plus forged X-Forwarded-For.
- T: An inbound email changes billing state, pausing collection on any 'offer' match (classify-email.ts:34-40). Mitigation: mustFix 5: remove the pause; later, pause candidates that need user confirmation and a 48-hour undo; the api role cannot rewrite inbound evidence.
- T, E: Prompt injection or model error puts invented claims into text sent to employers (tailor.ts:54,73; invented-details.ts:9-11). Mitigation: mustFix 7: the inventedDetails check on tailored lines; then a verifier that requires employers, titles, schools and dates to appear in the cited facts, an injection canary, and Autopilot refusing suspect jobs.
- I: Special-category personal data exposed to the model provider, the logs and plaintext columns (resume-parser.ts:35; drizzle errors.js:10-17; profile.ts:34). Mitigation: mustFix 6 and 9; the Anthropic DPA and ZDR; encryption with DATA_KEKS; scrubbing sensitive answers.
- T, R: Credit ledger or application history rewritten with no trace: one owner-level role, nothing append-only, no event log (client.ts:13; billing.ts:8-31). Mitigation: Per-process roles, UPDATE and DELETE revoked plus immutability triggers, application_events with the actor, the money journal and nightly drift checks.
- T: Credit fraud: $0 promo invoices, free grants re-farmed after account deletion, receipts asserted by the page or the client (billing-events.ts:74-83; auth.ts:106; cloud-apply.ts:61-65; extension.ts:31-34). Mitigation: Grant only on an amount paid or an allowlisted coupon, an email tombstone, a schema-validated report with the applicationId forced, leases, cross-checks against confirmation emails.

## Notes

Bottom line: mitigate. I approve continuing the build toward ADR-001, with conditions. The target security design (02-database section 4, 05-api sections 5-6, 06-infrastructure section 7) is sound, apart from one defect in the client-IP design in 05-api. Until the 11 mustFix items are closed and verified on staging, three things are blocked: public launch, real users' data in sd1, and cloud-channel sends for anyone but you.

The core problem is order. The cloud applier is live now, but its protections are scheduled for P5. The resume-suite PRD (D7) puts file import and rendering on today's server before the P3 parser limits exist.

The risk in plain words: one process opens strangers' web pages in a browser with its sandbox off, while holding the main database password and every API key. One browser bug on one employer page means a breach of every user's resume, answers and account, plus the Stripe and Anthropic keys. Separately:
- anyone can freeze the API with a request of about 50 KB;
- one script can lock sign-in for everyone;
- a free account can spend hundreds of dollars a day on Sonnet;
- a forwarded email can pause a customer's billing.

The numbers (estimates):
1. Applier breach: about $150-170 per record → about $0.15M at 1k users, $1.5M at 10k, plus abuse of the stolen keys. I put the chance at 5-15% a year while the browser is unsandboxed, URLs are unchecked and Chromium is frozen at the image build. Expected annual loss $10k-$225k. Fixing it takes 3-5 engineer-days; switching the cloud channel off meanwhile costs nothing.
2. AI spend abuse: about $160 expected, up to $720, per scripted free account per day per replica. One large imported board at 10k users costs $4-5k in scoring. I put a 30-50% chance on at least one such event in year one, and with no spend alerts it runs until the invoice arrives. Expected annual loss $5k-$50k. Fixing it takes 1-2 days; the Console spend cap takes minutes.
3. API freeze and sign-in lockout: near-certain once someone scans the API, or on launch day. The cost is hours down times lost sign-ups. Fixes take under a day and 1-2 days.
4. Offer-pause fraud: one plan-month per abusing subscriber per month. The fix is deleting 7 lines.
