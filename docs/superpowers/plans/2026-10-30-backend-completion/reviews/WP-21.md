## Decisions the builder made that reviewers should check

1. **"Counts under 5 hidden" reads as the PRD's rule, not its words.** `work-packages.md` says counts under 5 are hidden. PRD 9.6, the R4 acceptance ("insights show counts below 5"), `insightsSchema` and `mock-contract.test.ts` (`small.sent === 3`) all show counts and hide rates. These are one user's own numbers, so there is no privacy reason to hide a count. Built: below 5 sent in a group, every rate is null, and so is the median, on every path. Since no count is suppressed, no total can give one back. The counts do let a client compute the rate; the PRD accepts that. If hiding counts is really wanted, it is a contract change: `sent`, `replies` and `interviews` must become nullable.
2. **A pipeline stage can be dropped on when the application's status already says it.** PRD 9.1 says a Kairos application cannot be dropped into Drafting or Applied. Taken literally, a mis-drag of a sent application to Saved can never return: `sent` fires once and the move is forward-only. So Applied is allowed when `status = 'submitted'`, Drafting when `draft` or `failed`. Applied is refused for every other status, approved and submitting included. Rule 11 and the anti-goal ("Applied without a submission report") still hold. The mock refuses both always; the hand-off says so.
3. **The projector follows `stageChanged`, not the reply kind.** That payload already carries WP-24's authority gate, so mail that could not move `applications.stage` cannot move a card, and a reply to an application still `submitting` waits.
4. **Each projector pass starts five minutes behind the newest event (round 1, D1; first built as a 1000-id overlap).** Identity ids are taken before commit, so a plain `id > cursor` skips an event that commits late. The xid8 snapshot method fails after a logical restore (`pgbackup.ts` dumps), because the xid counter restarts below the stored values and the cursor would stall silently. Replaying is safe because `applyEvent` is forward-only and `tracker_items.user_moved_at` is a floor: an event at or before the user's last move does nothing. Ceiling in the `ponytail` comment.
5. **The undo reaches the card through the projector.** `stage/clear` is unchanged. Its `stage_changed {undone: true}` event moves the card back only if the card's stage is one mail set (`stage_set_by = 'system'` and interviewing, offer, or closed as rejected), to Applied or, for `to: null`, Drafting. A stage the user chose stays. The worker therefore writes `user_moved_at`; the column grant is in the script.
6. **The worker's SELECT on `tracker_items` is now column-limited**, without `notes`, `salary_text` and `job_snapshot`. Its grant comment said "never the user's notes" of UPDATE only, while it could read them; the worker runs agents, and database-123 asks for this. On `contacts` and `interviews` it holds `(id, user_id)`, which is what `jobs/erasure.ts`'s zero-row check reads. The matrix cell for `tracker_items` changes from `SI` to `I`.
7. **`recordEvent` now writes `job_snapshot`** when it creates a card, because the worker cannot write it later and PRD 9.3 wants the posting kept. This is the one change to the event path and no producer changed. A card from before this reads the live description on the detail, and loses it when retention purges a closed job.
8. **`GET /api/applications/:id/events` answers the shared event shape**, the same as `/tracker/:id/events`, not 05-api's `{id, kind, actor, at, detail}`: `{events, nextCursor?}`, `at asc, id asc`. It reads by tracker item, so the item's saved and note events are in it, which `application_events_app_idx` would miss (a `saved` event written before the application existed has a null `application_id`). That index is therefore not used by this route; `application_events_item_idx` is. 05-api is amended.
9. **`sendFailedRefunded` is false for an ambiguous failure** (`unconfirmed`, `timeout`, `no_report`) and for a null code. "Send failed, credit refunded" would be untrue when the mail may have gone, and could prompt a duplicate.
10. **`.ics` times are UTC with `Z`** (RFC 5545 form 2), as the mock and its test have it. That is an explicit instant and needs no VTIMEZONE block. The zone the user chose stays on the API.
11. **Position default.** `tracker_items.position` now defaults to the insert time in milliseconds, so new cards sort after old ones and rarely tie. Keys are checked as `^[0-9A-Za-z]{1,64}$`. `positionBetween` is in `shared`, for the web. It never rebalances; ceiling in its comment.
12. **Replies in insights come from `inbound_emails`, not events.** An undone reply is detached but its event is immutable, so counting events would keep counting it. `other` counts as a reply, as the PRD's words say.
13. **List rows carry `salaryText: null`.** The schema requires the key and the WP-16 hand-off says it is not in list rows. The detail carries it.
14. **Per-user caps** I chose: 5,000 cards, 5,000 contacts, 100 interviews a card, as `409 limit_reached`. Count then insert, so a race passes by a few.
15. **One `note_added` an hour per item**, by dedupe key, so autosave does not fill the timeline.
16. **No retention key.** PRD 9.4 and 12: contacts and interviews live until the user or the account deletes them. `test/retention.int.test.ts` is unchanged.
17. **No encryption on contacts.** Search over name, company and title needs plaintext. Protected by role grants: only the api reads them.
