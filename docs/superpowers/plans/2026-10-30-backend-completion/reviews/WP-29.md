## Decisions the builder made that reviewers should check

1. **Settlement has no queue and no outbox row.** The spec has a `settle` queue fed by the applier. An attempt with `settled_at IS NULL` is already a durable work item, so the worker's lease sweep (every 30 s, `processSweepSubmitting`) settles every closed attempt. No new queue, no new consumer, no `OUTBOX_QUEUES` entry, no `kairos_worker` INSERT on `outbox` (the WP-22 hand-off's grant was conditional, and the condition is not met). Cost: a cloud send's result shows up to 30 s after the run ends.
2. **The replay does not close the attempt.** The spec's `reason: "replayed"` closes by phase at once. Under BullMQ a stalled job is redelivered while the first run may still be alive, and closing then would turn a real send into "unconfirmed". A delivery that loses `mark_browser_launched` returns skipped and leaves the attempt to its own report or the heartbeat (90 s).
3. **`mark_attempt_phase` returns a boolean and the run stops on false** (spec: void). The sweep can close a run in `navigating` as `applier_error`, "nothing was sent", which is resendable with no acknowledgement. If that run kept going and clicked, the next resend would be a duplicate nobody was warned about. So the mark of `filling` is the gate: it commits before the fill, and a closed attempt refuses it.
4. **A late `submitted` from the applier moves an ambiguous attempt forward** (spec 5.7: a no-op). If the sweep closed a live run as unconfirmed and the run then saw the confirmation, dropping that would tell the user "check your email" about a send we know arrived. `record_attempt_result` moves it, clears `settled_at`, and settlement records it. A non-ambiguous attempt stays final.
5. **A late result also stops a resend that has not gone out.** Settlement moves `approved` to `submitted` when an older attempt turns out to have reached the employer, and the queued job then finds nothing approved. If the resend has already been claimed, it cannot be stopped: `submission_dual_detected` pages.
6. **The first claim wins, for a second tab of the same session too** (05-api 13.3 answered that repeat 200; amended there). The acceptance says two tabs cannot send, and tabs share a session. A client that lost the response releases and claims again.
7. **A release moves the application to the next attempt number** (spec: keeps it). The released row is final under `submission_attempts_app_attempt_uq`, so a later claim or report at that number would collide with it.
8. **No `ap2_verified` branch and no route interception of the apply POST** (applications-60). It needs per-ATS proof on a throwaway posting that nobody can run here. Without it `submit_seen` is never written and `filling` always reads as ambiguous, which is the spec's own table before S-AP2 passes. `mark_attempt_phase` accepts `submit_seen`, and rule D2 is in place for when it arrives.
9. **`record_attempt_result` accepts `unconfirmed`** beside `timeout` (spec: the applier never reports an ambiguity). The run knows a fill was interrupted, and reporting it as `timeout` would change the sentence every test pins. It can still not report `no_report`.
10. **The read before the claim is a function with no content (`applier_job`), and content comes from `get_applier_payload` for an open attempt only** (spec: a view of every pending row's answers). Narrower. Known limit: nothing binds an attempt to a job id, so a compromised applier can claim any pending cloud row and read that row's answers. It cannot reach a row with no pending cloud send.
11. **A resend reuses the stored snapshot** (arch B.6.4 as amended; the comment in `db/schema/applications.ts` says a new one). The user approved that document, and its rendered file stands. Written only when absent, on rows failed before this release.
12. **Facts drift has two arms.** A hash comparison when `facts_snapshot_hash` is set, which only WP-41 will write, so the check that bites today is that every cited fact is still the user's and confirmed. That made the old fixtures' `factIds: ["f1"]` skip as `facts_changed`, so approve-path fixtures now use `factIds: []`. `factsSnapshotHash` is exported for WP-41.
13. **The link's button is the acknowledgement for an ambiguous code** (spec: a checkbox). `signedLinkRouter` renders one button and no fields, and the page says what pressing it means. A refusal (no credits, closed) rolls the link's use back through a new `LinkRefusal`, so the link still works after the user buys credits; the spec consumes it.
14. **No `Idempotency-Key` (api-auth-security-47, v06, tests-27).** Approve is state-conditional, so a retry cannot charge twice, and a draft approved on the same channel in the last minute is answered as approved, which covers a double click and a lost response within a minute. The key needs a table of stored outcomes for 14 days, which was a workflow engine's free feature and is not here. Add it if a client asks for replay across minutes.
15. **I-1 pages and does not freeze** (A-SUB-2 freezes). One user's extension reporting twice could otherwise stop every user's approvals.
16. **`approvals_frozen` stays a 503 and `extension_only` a 409** (spec: skips). WP-27 pinned those; changing them is a contract change with no gain here.
17. **Return-to-draft writes no event**, as 08 section 13 item 1 says, until the kind exists. Its lost-email reconcile is a query: a draft with `attempt_no > 0` was returned.
18. **Draft expiry is in** (applications-44, in the cited refs). It has no `applications_draft_age_idx`; `ponytail` comment with the ceiling.

## Deploy window

Expand-only: migration 0027 adds functions and touches no table. Each mix was walked through:

| Mix | What happens |
|---|---|
| New schema, old api and applier | Unchanged. Old writers set no attempt row, attempt number or snapshot, and no new check refuses that |
| Old approve (`attempt_no` 0), new applier | The claim moves it to 1. The job has no `attemptNo` and means the current attempt |
| Old outbox row `apply-<id>`, new reconcile | The reconcile reads both key forms, so it leaves a live old row alone |
| Old claim, no attempt row, new sweep | `repairLegacyRows`: past 8 minutes it is failed, unconfirmed, as before |
| Old failure with no code, new resend or report | The sweep fills the code each tick. Until then a resend treats a null code as ambiguous, and a late report gets 409 |
| New claim, old worker's sweep | At 8 minutes the old sweep fails it with no code. The new sweep closes the attempt, settlement sees the application moved on, and the repair fills the code |
| Script re-run before the new applier is up | The old applier cannot claim: jobs fail and retry, nothing is sent. `owner-actions/WP-29.md` parks them with `pause_cloud_apply` |

## What each guard test really exercises

The fixture pool runs as actor `ops`. `applications_guard_status`, `submission_attempts_guard` and `applications_guard_snapshot` read no actor, so those fixture-pool tests prove them. `applications_guard_stage` does read it: the stage undo test sets `user` itself through the application's pool, and the refusal goes through that pool with no actor. `matches_status_guard` too: the queue route tests use the app's own pool with `asActor`. The late-confirmation pair `failed -> submitted` runs under the fixture's actor and needs none.
