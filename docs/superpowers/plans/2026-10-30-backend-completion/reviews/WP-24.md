### Limits of the authority gate (item 1), stated rather than solved

- **Any customer of an ATS signs with its domain.** The ATS allowance is needed because real rejections mostly come from the ATS, and Tier 2 asks for the company's name as well. Someone with a tenant on the same ATS who knows the forwarding address can still set a terminal stage.
- **Replay.** A genuine signed rejection that another applicant received can be re-sent to a victim's address, within 30 days of signing when it carries `t=`. Requiring the signed To to match isn't possible here: an auto-forwarded mail is addressed to the user's own mailbox, which Kairos may not know.
- **Recourse is the user's undo (round 2).** It helps only someone who notices; the tracker UI is WP-21's, and there is no web button yet.
- **A `domain` link alone is not proof.** A fake forward block from free mail earns one (`originalSender`), and the verdict is what stops it. Whoever builds offer-pause candidates must read `verified_domains`, not `linked_by = 'domain'` as workers/10 B6 says.
- **A manual forward never has authority.** It tags the mail and leaves the stage, so a user who only forwards by hand won't see rejections move it.

**Design of the undo, for Security and DB:**

- **Any stage, not only `rejected`.** The ruling named `rejected` to NULL. I allow any stage to NULL for a user actor: a forged signed offer blocks the forward path too, and an unsigned interview is just as wrong to its owner. Every other backward move stays refused, for a user too; the only move a user gets is the clear. Say if you want it narrowed to `rejected` and `offer`.
- **The guard.** `applications_guard_stage` allows `NEW.stage IS NULL` only when `kairos_actor() = 'user'`. No worker sets that actor; only `asActor(tx, "user")` in a request does. The int test tries none, empty, `system` and `ops`, and a user moving backward to a non-null stage.
- **Detach needs a new api grant.** `UPDATE (application_id, linked_by) ON inbound_emails`. This loosens "the api cannot rewrite inbound evidence": it can now unlink a reply, though not change what it said, its tag, its verdict or when it came. The offer-pause candidate rows WP-46 or later adds should keep their own `application_id`. `has_table_privilege` stays false for a column grant, so the matrix cell is unchanged; three new statement cases cover it.
- **What detach does not do.** The `reply_*` event stays, because events are immutable, and the undo event sits after it. The `reply_important` notification stays too.
- **No re-apply.** A classified row never classifies again (`classified_at IS NULL`), and a redelivery finds the row and queues nothing. The test covers both.
- **Not session-fresh.** It moves no money and no access, and touches only the caller's own tracking. An attacker with a stale session gains nothing they couldn't get from the other application routes.
- **No new error code.** It answers `not_found` and `invalid_param`, both already in the catalog.
- **`stage` on `GET /api/applications/:id`.** Added beside `application`, not in it: `test/serializers.test.ts` freezes `APPLICATION_COLUMNS`. Without it nothing could show which stage there is to undo.

## Known ceilings

- The caps count then insert, so concurrent deliveries can pass them by a few rows. A per-user advisory lock with the count in the insert transaction makes them exact if that ever matters.
- A failing body-size gate answers 503 `Retry-After: 3` (`bodyPermit`'s value), not the spec's 5. Postmark retries either way.
- `inbound_body` retention can't use `inbound_emails_body_purge_idx` while it also looks at the legacy plaintext. That goes with the column in WP-46.
