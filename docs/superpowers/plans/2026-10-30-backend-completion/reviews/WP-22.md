## Decisions the builder made that reviewers should check

1. **Completion is read from BullMQ, not written by the consumer.** A job in state `completed` finishes its row, in the sweep. A.11 has the effect and a completion mark share a transaction; with idempotent consumers that adds nothing, and it would need an outbox grant on `kairos_applier`, the process that opens hostile pages. Cost: a row shows `enqueued` for up to a minute after its job finished, and a completed job evicted before the sweep sees it is delivered once more, which an idempotent consumer skips.
2. **Keys use hyphens: `apply-<id>`, not A.11's `apply:<id>:<n>`.** BullMQ refuses a job id with a colon unless it has exactly two, so `settle:<id>` and `stripe:<id>` would throw at add time. `outbox_key_ck` and `emitOutbox` enforce it.
3. **A refused add spends no attempt.** Redis being down delays the work and must not push every approval to dead. The row retries every 5 s; `outbox_lag` fires from the drain loop itself, because the alert evaluator is a BullMQ job and cannot tick during that outage. Only deliveries that came to nothing (job failed for good, or lost) count, up to 5, with 30 s, 1, 2 and 4 min between them.
4. **The drain holds its row locks over the Redis calls**, each under a 10 s deadline (the worker role's idle-in-transaction limit is 30 s). A crash rolls the mark back and the re-add is a no-op on the job id. A lease column would avoid the open transaction at the cost of a second recovery path.
5. **The stuck-submitting sweep moves from 10 to 8 minutes** (`sweepStuckSubmitting`, WP-09's). At 10 it settles up to 10.5 minutes after the claim, so the acceptance's "terminal within 10 minutes" could not pass for any run killed in the browser. A run is bounded at about 3 minutes plus its 170 s shutdown drain. Known ceiling: a job killed before its claim is redelivered after the 4-minute lock, and if that second run is also killed in the browser it settles about 13 minutes after approval. The harness reports it if it happens. WP-29's leases replace this sweep.
6. **The drain is a 1 s loop in `worker.ts`, not a maintenance schedule**, so it does not add a job a second to Redis or push other tasks out of the maintenance queue's retained history. One more pool connection per worker replica.
7. **`reconcile-apply` stays, narrowed.** It leaves any application with a live or dead outbox row alone (a dead row is for an operator; re-adding its job would defeat the bound) and still nets rows approved before this release, or by the old api during a rolling deploy.
8. **Scope of the wiring: approve and applyCloud only.** Settle, Stripe processing and offer-pause have no durable flow to move yet; each package emits through the same call. `kairos_worker` holds no INSERT on `outbox` until one of them needs it, so WP-29 adds that grant if settle emits from the worker.
9. **Not in the privacy registry, on purpose.** An entry with no `by` is read as user-keyed, and the erasure worker would compare the jsonb column to a user id and throw. The table holds no user id: `emitOutbox` and invariant OX-1 both refuse a `userId` field, so a consumer reads the owner from the row the payload names.
10. **`reason` on resume is a code, `^[a-z0-9_-]{3,64}$`.** 05-api A-11 asks for a written reason on admin writes, and it lands in `ops_audit.after`, which the nightly PII scan reads as holding no free text.
11. **The harness omits the apply gate.** It limits rate per ATS and has no part in durability, and a killed process's slots would only slow the run.

## What has not run

No Postgres, Redis or Docker on the build machine. So `outbox.int.test.ts`, the changed int tests, the migration and the grants have never executed; CI is their first run. The chaos harness has never run at all: its entry points were only loaded far enough to reach their argument checks.
