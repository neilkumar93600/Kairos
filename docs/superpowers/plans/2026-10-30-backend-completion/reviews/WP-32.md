## What is built

- **Store then process** (billing-12 to 17). `POST /api/webhooks/stripe` verifies, stores `stripe_events` in `received` with a minimized payload and an outbox row in one transaction, and answers. It never calls Stripe. The `stripe` queue (outbox-fed, 8 tries) runs `processStoredEvent`; a state no retry can fix is `dead` at once and pages; `processStripeSweep` (5 min) reopens a row whose job gave up, up to 6 times 12 hours apart, then `dead` with `retries_exhausted`.
- **Ordering** (billing-19). Per customer, one event at a time: the customer's advisory lock is held from before the refetch to the commit. The guard `subscriptions.stripe_event_created` ignores an event strictly older than the one applied. **Two events in the same second** are both processed; that is safe only because of the lock: whichever runs second refetches after the first committed, so it cannot put an older snapshot back. `webhooks.int` has a test with a slow first refetch that would lose without the lock.
- **Minimized payload** (billing-14). An allowlist per kind, ids and integers only, zod-checked, under 4 KB by construction (lines cut at 20, `linesTruncated` fetches the rest). The only person's id is the invoice metadata `userId`; `PRIVACY_REGISTRY` has `stripe_events` (cascade) and erasure scrubs rows not yet tied to the user by customer id. A `user_deleted` row keeps neither id. Unit test with marker names, emails and addresses in every event type.
- **`credit_balances`** (billing-38, database-79) with the two definer triggers, backfilled under a SHARE lock in the migration. Reads (`/api/me`, `/api/credits`, approve) are one primary-key row.
- **Rule L1** (billing-39, applications-36). WP-29's advisory lock is gone from all four places it was (approveCore, settleAttempt, the report, returnStaleApprovals); each takes `lockCreditBalance` first. Also now first: withdraw, the legacy repair (per user), erasure (before the applications and the user), sign-up's free grant, the grant and the sync.
- **Rollover** (billing-37): `max(0, balance - in_flight - 2 x grant)` under the lock, only when the grant row was really inserted.
- **billingReconcile** (billing-55, 56, v07), daily 04:15: missing grants over 7 days, subscription drift (synced from a fresh refetch under the customer lock), double-live count, grace expiry count, price drift against `plans.ts`, balance drift.
- **LEDGER-2** (nightly, freezes) and **BILL-7** (hourly, pages) in `jobs/invariants.ts`.
- **Operator CLI** `scripts/ops-billing.ts` (billing-43): `dead`, `adjust`, `refund`, `redrive`, `repair-balance`, each with its `ops_audit` row.
- **`GET /api/credits`** (billing-59): one repeatable-read snapshot and a keyset `nextCursor` (additive; 05-api already lists it).

## The lock order, and why it has no cycle

One order: Stripe customer advisory lock < `credit_balances` row < `subscriptions` row < `applications` rows by id < `submission_attempts` < everything else (events, outbox rows, inserts). The cycle that matters: the in-flight trigger updates the balance row **after** an application row's status change, so any path that holds an application row and then crosses the boundary waits on the balance row.

| Path | Takes | Crosses the in-flight boundary? |
|---|---|---|
| approveCore (approve, resend, signed link) | balance, then applications sorted by id, then outbox insert | yes, under the balance lock |
| settleAttempt, the extension report | balance, application, attempt | yes, under the balance lock |
| withdraw | balance, application | yes |
| returnStaleApprovals | balance rows sorted by user id, then the applications | yes |
| repairLegacyRows | one transaction per user, balance first | yes |
| processStoredEvent (grant, sync) | customer lock, balance, subscription | no application row |
| claimForExtension, releaseForExtension, `claim_cloud_attempt` | application, then attempt | no: approved and submitting are both in the set, so the trigger leaves the balance alone. They hold an application and wait only on an attempt row, never on a balance |
| record_attempt_result, mark_*, closeStaleAttempts | one attempt row | no |
| leaseExtensionQueue | applications, SKIP LOCKED | no; it never waits |
| eraseUser | balance, the user's applications by id, then the user and the cascade | the cascade deletes in-flight rows; their trigger only updates, never inserts, so it cannot fail the foreign key |
| bootstrap's free grant | balance, then profile and ledger | no application |
| classifyEmail's stage write, the stage undo, PATCH draft (WP-21) | one application row, no status change | no |

A cycle needs a path holding something late in the order while waiting on something earlier. Every path that waits on a balance row holds nothing but its customer lock; the paths that hold application rows without the balance (claim, release, the cloud claim) never wait on a balance; nothing holds a subscription or an attempt and then waits on a balance or an application. One I found while writing the test and fixed before committing: `processStoredEvent` locked its event row and then took the balance, while erasure takes the balance and then writes those event rows. It no longer locks the event row (the customer lock serializes a job delivered twice).

Erasure also used to deadlock against a claim or a settlement on its own, before this package: it held the user row, the cascade waited on an application, and that path's insert waited on the user's foreign key. Taking the balance and the applications first removes that.

`test/lock-order.int.test.ts` is the proof (T-DB-2): a control that does the wrong order on purpose and must see exactly one deadlock, then 1,000 rounds of 17 shuffled paths for one user with `pg_stat_database.deadlocks` unchanged and the cache equal to its recount, then 100 rounds of erasure against a report, a claim, a settlement and a grant. **It has never run.**

## How the cache cannot drift without anyone noticing

The triggers fire on every ledger insert and every status change, whatever role or release wrote it, including the previous release during the deploy. No runtime role may write the table (provision-roles, applier-role.int). What is left is a write as the owner or migrator, a restore that loses it, or a bug in a trigger. LEDGER-2 recounts every user nightly from `"user"`, not from `credit_balances`, so a missing row counts too, in one statement, so work in flight is never a false positive; it pages and freezes approvals. The daily reconcile reports the same count. `credit-balances.int` corrupts a balance, an in-flight count, deletes a row, and checks a later correction does not hide it.

## Decisions the builder made (owner delegated)

1. **The outbox, not DBOS**, carries the stripe queue, as ADR-001 Revision 3 decided for money.
2. **Per-customer serialization by a transaction-scoped advisory lock held across the refetch** (at most 10 s, at most 4 per worker replica), not BullMQ groups (a paid feature) or a lease table.
3. **Anomalies go dead at once** and page; they used to be 500s that Stripe retried for 3 days. An operator fixes the cause and redrives.
4. **No `billing_cache_reads` shadow week and no `LIFECYCLE_V2` flag.** The triggers keep the cache right from the migration on, including the old release's writes, and LEDGER-2 checks it nightly. The old inline webhook path is gone in this release.
5. **The advisory lock is removed outright**, not kept beside the balance lock for one release. During the deploy minutes an old-api approval and a new-api approval for the same user could both pass their check, at worst a few credits over-reserved; BL-1 and BL-2 page on it.
6. **Retry rounds**: 8 tries in the job, 5 outbox deliveries, then up to 6 reopenings 12 hours apart: about 60 hours, close to Stripe's own 3 days.
7. **Both triggers upsert** (spec: the in-flight trigger only updates), so no user with a ledger row or an in-flight application can lack a row; a DELETE only updates, for the erasure cascade.
8. **`ensure_credit_balance` makes nothing for a missing user** instead of failing its foreign key, so a request whose account was erased meanwhile answers as for no rows.
9. **A grace expiry is counted, not acted on**: `effectivePlan` already reads the anchor. WP-36 adds the Autopilot pause.
10. **The reconcile acts on a local subscription Stripe no longer has** (cancelled, free) and on one live untracked subscription per customer; with two live it only reports.
11. **The rollover cap follows the new invoice**, as the spec's formula: a move to a smaller cycle writes off everything above twice the new grant at its first renewal. The billing runbook says so.
12. **No `syncStripeSubscription` queue**: the reconcile syncs inline under the customer lock, which gives the same ordering.

## Deploy window

| Mix | What happens |
|---|---|
| New schema, old api and worker | Unchanged. The old insert names neither status nor processed_at and gets `processed`; the consistency check does not ask it for an outcome. Old ledger and status writes keep the cache right through the triggers |
| New api, old worker | Events are stored and wait; the old drain leaves a row of a queue it does not know |
| Old api, new worker | The old api processes inline, as before; nothing is `received` |
| New code before provision-roles | The default privileges give the runtime roles the new table and EXECUTE on the function, which the code needs; the script narrows them |
| Rollback of the api after events were stored | Those rows wait for a worker of this release (owner-actions step 1) |
