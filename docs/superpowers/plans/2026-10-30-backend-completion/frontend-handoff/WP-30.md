# WP-30 frontend handoff: API hygiene and contract

No file in `web/` was edited. Four changes are visible to the web; only the first needs web work.

## 1. `403 reauth_required` on billing now; on approve later (needs web work before approve is switched on)

`POST /api/billing/checkout` and `POST /api/billing/portal` need a session created in the last 24 hours. An older session gets:

```json
{ "error": { "code": "reauth_required", "message": "Sign in again to continue", "details": { "maxAgeSec": 86400 }, "requestId": "..." } }
```

Sessions last 30 days and `createdAt` never moves, so a returning user hits this on their first checkout. Today the web shows `message`, with no way to act. Wanted: on `ApiError.code === "reauth_required"`, a "Sign in again" button that signs out and returns to `/sign-in?next=<current path>`, keeping the pending plan choice.

`POST /api/applications/approve` is also a session-fresh route, but its 24 h age check is OFF (env `FRESH_SESSION_ENFORCE`, default false) until `hooks/use-applications.ts` handles `reauth_required` the same way. Approve already reads the session without the cookie cache, so a revoked session is refused at once. Ops turns the age check on with `FRESH_SESSION_ENFORCE=true` once the web ships. The extension is unaffected.

## 2. Lists accept `limit` and `cursor`, and may return `nextCursor` (additive)

`GET /api/matches`, `GET /api/applications` and `GET /api/inbox` take optional `?limit=1..200&cursor=<opaque>`. With neither, the answer is the same first page as before (100, 200 and 100 rows). When more rows exist the body gains `nextCursor`; pass it back as `cursor` for the next page. A bad `limit` or `cursor` (wrong type, malformed, or from another list) is `400 invalid_param`. Cursors are opaque: do not build or edit them. The web ignores the new field today, so it still shows only the first page; "load more" can use it later.

`GET /api/applications` rows gain `updatedAt` (ISO string). Nothing else in a row changes.

## 3. New response headers and CORS

Every `/api` response carries `Kairos-Contract: 2026-11-03`. Cross-origin requests may send `X-Kairos-Client`, `Idempotency-Key`, `If-Match` and `If-None-Match`, and browsers can read `Retry-After`, `RateLimit`, `Kairos-Allowance` and `Kairos-Contract`. The web is same-origin through the rewrite, so nothing changes for it.

## 4. New error: `503 timeout`

A route that exceeds its server deadline (10 s default, 15 s for `PATCH /api/applications/:id`, 30 s for fit and approve, 40 s for `/api/billing/*` (up to four Stripe calls), 60 s for the model-backed routes) answers `503 timeout` with `Retry-After: 5`. The web treats any non-2xx as an error and shows `message` ("This took too long. Try again."), which is enough.

Also: the model-backed routes (`/resume/suggestions`, `/jobs/:id/tailor`, `/applications/:id/drafts`) now share one 10-a-minute `ai_burst` count per user across all api replicas, (`/jobs/import` shares that bucket, per 05-api 6.2), so a 429 `rate_limited` with `details.bucket = "ai_burst"` can arrive slightly earlier than before when the api runs on several instances. The status and code are unchanged.

A unit of AI allowance taken by a request that then times out is given back, and the model call is aborted through the deadline signal at the three AI call sites.

Not mounted yet: `bodyPermit` (middleware/deadline.ts), a per-replica cap on concurrent large bodies. WP-17's upload route should mount it before its body parser.
