# WP-02 frontend handoff: sign-in on the web

The API side is on branch `wp/02`. The web part below was not changed by WP-02 (web/ was out of scope for this package).

## 1. Show only the providers the API has configured

New public route, additive to the frozen contract:

```
GET /api/auth-providers  ->  200 { "providers": ["email"] }            // Google not configured
                         ->  200 { "providers": ["email", "google"] }  // both GOOGLE_* set on the api
```

The type is exported from `@auto-career/shared`: `AUTH_PROVIDERS` and `AuthProvider` (`"email" | "google"`).

- `web/components/auth/login-form.tsx:44` and `web/components/auth/sign-up-form.tsx:74` render `<GoogleButton />` unconditionally. Render it only when `providers` includes `"google"`. Fetch once per page load (same origin, through the `/api` rewrite). On a failed fetch, show email only.
- Do not add Apple, GitHub or LinkedIn buttons; they stay hidden until WP-38. If the settings "sign-in methods" screen is built later, drive it from the same list.

## 2. Fail the Vercel production build when API_ORIGIN is unset

`web/next.config.ts:4` falls back to `http://localhost:4000`, and rewrites are fixed at build time, so a production build without `API_ORIGIN` ships a dead `/api` proxy. Throw at config load when `process.env.VERCEL_ENV === "production"` and `API_ORIGIN` is unset or not `https://`. Keep the localhost fallback for local and CI builds (`.github/workflows/ci.yml:22` sets `API_ORIGIN=http://localhost:4000` without `VERCEL_ENV`).

```ts
const apiOrigin = process.env.API_ORIGIN ?? "http://localhost:4000";
if (process.env.VERCEL_ENV === "production" && !process.env.API_ORIGIN?.startsWith("https://")) {
  throw new Error("API_ORIGIN must be set to the https Railway api origin for a production build");
}
```

## 3. Nothing else changes for the web

- The Google redirect already goes through the web origin: `authClient` has no `baseURL`, so `/api/auth/sign-in/social` and the callback `/api/auth/callback/google` run on the web host.
- Passwords longer than 128 characters now fail with `PASSWORD_TOO_LONG` (400). The sign-up and reset forms can cap the input at 128 (`maxLength={128}`) to avoid a round trip.
- A password reset now signs out every session. The reset form already sends the user to `/login?reset=1` (`reset-password-form.tsx:40`), so no change is needed; other signed-in tabs will get 401 and should land on `/login` as they do today.
- Google sign-in for an email that has an unverified password account fails with `error=account_not_linked`. Today that lands on Better Auth's own `/api/auth/error` page. Pass `errorCallbackURL: "/login"` to `authClient.signIn.social` in `google-button.tsx:14` and, on `/login?error=account_not_linked`, show: "This email has an unfinished sign-up. Sign in with your email and code first."
