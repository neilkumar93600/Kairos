# WP-03 frontend handoff: the edge headers and the new 429 and 413 answers

The API side and the one web change are on branch `wp/03`. Nothing else in `web/` was changed.

## 1. Done in this package: `web/proxy.ts` now runs on `/api/*`

`proxy.ts` matches every `/api/*` path except `/api/webhooks/*` and, before the `next.config.ts` rewrite sends the request to Railway, sets two request headers:

| Header | Value |
|---|---|
| `x-kairos-edge` | `process.env.KAIROS_EDGE_SECRET` (server-only, set on Vercel by the owner) |
| `x-kairos-client-ip` | Vercel's own `x-real-ip` for the browser |

Both are first removed from the incoming request, so a browser cannot send its own. Without the secret (local `next dev`) both are dropped and the api keys on the address it sees, which is fine locally. Tests: `web/test/proxy.test.ts`.

Things to keep in mind when you touch `proxy.ts` or `next.config.ts`:

- Keep the `/api` branch first in `proxy()` and keep the `"/api/((?!webhooks/).*)"` matcher entry. If `/api` drops out of the matcher, every browser is keyed on Vercel's address again and shares one bucket, sign-in included.
- Never read or forward `KAIROS_EDGE_SECRET` anywhere else, never prefix it with `NEXT_PUBLIC_`, and never call the Railway api directly from server code with it: all API traffic goes through the rewrite.
- A proxy buffers request bodies in memory, up to 10 MB by default (`experimental.proxyClientMaxBodySize`), and cuts anything longer without an error. Webhooks are excluded for that reason. Any future upload through `/api` above 10 MB needs that limit raised; the resume upload cap (5 MB, CISO mustFix 8) fits.
- `next.config.ts` is unchanged; no new web variable is needed beyond `KAIROS_EDGE_SECRET`.

## 2. Express API 429s: one envelope for every limit

Every rate-limited Express route now answers:

```
HTTP 429
Retry-After: <seconds>
{ "error": { "code": "rate_limited", "message": "Too many requests. Try again later.",
             "details": { "reason": "ip_limit" | "user_limit", "bucket": "anon" | "user_api" | "billing" | "contact" | "webhook_ip", "retryAfterSec": <seconds> } } }
```

`ApiError` in `web/lib/api.ts` already carries `status`, `code`, `message` and `details`, so nothing breaks. The limits a signed-in user can meet:

| Bucket | Limit | Where it can show |
|---|---|---|
| `user_api` | 600 per minute per user, every signed-in route | Practically never; a runaway polling loop would. |
| `billing` | 10 per 10 minutes per user, `POST /api/billing/checkout` and `/portal` | The plan and billing buttons. Suggest: on 429 with `bucket === "billing"`, show "Too many attempts. Try again in N minutes" with N from `retryAfterSec`, and disable the button meanwhile. |
| `anon` | 120 per minute per address, requests without a session | Signed-out pages that call the API (`/api/auth-providers`, already cached 5 minutes). |
| `contact` | 5 per hour per address | `contact-form.tsx` already handles 429 by status. |

The AI-route limits (`writerLimiter`, `importLimiter`) are unchanged in this package and still answer their own messages without `details`.

## 3. Better Auth 429s on sign-in, sign-up and code mails

Better Auth routes keep Better Auth's own shape (05-api 4.6). The auth client returns them as `error.status === 429` with `error.message`, and the forms already show `err.message`, so each case below already shows a message; the suggestions only make it friendlier.

| Limit | Applies to | Message today |
|---|---|---|
| 5 per minute and 20 per hour per email | `signIn.email` | "Too many attempts for this email. Try again later." |
| 3 code mails per 10 minutes per email, shared by every path that mails a code | `emailOtp.sendVerificationOtp`, `emailOtp.requestPasswordReset`, `forgetPassword.emailOtp`, `sendVerificationEmail` | Same as above. |
| 3 sign-up attempts per address per day | `signUp.email` | "Too many requests. Please try again later." (header `X-Retry-After`) |
| 20 sign-ins per minute, 10 code mails per hour, 60 other auth calls per minute, per address | the matching auth calls | Same as above. |

Suggestions:

- `verify-otp-form.tsx` (resend) and `forgot-password-form.tsx`: after a send, disable "Send a new code" for 60 seconds with a countdown, so a user does not burn the 3 sends in 10 minutes by double-clicking. On 429 show: "We've sent several codes already. Check your inbox and spam, or try again in 10 minutes."
- `sign-up-form.tsx`: on 429 show: "Too many sign-ups from this network today. Try again tomorrow, or sign in if you already have an account." (The cap is under review with the owner, so keep the wording generic.)
- `login-form.tsx`: on 429 show the message as is; do not route to `/verify-otp`.

## 4. 413 on `/api/auth/*`

Any `/api/auth/*` request with a body over 64 KB, or a body without a declared length (chunked), now answers 413 before Better Auth sees it:

```
{ "error": { "code": "payload_too_large", "message": "The request body is too large" } }
```

The auth forms send a few hundred bytes, and `fetch` with a string body always declares its length, so this never happens to the web. Nothing to change; do not send auth requests with a `ReadableStream` body.
