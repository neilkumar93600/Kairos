# WP-24 frontend handoff: reply forwarding panel and inbox

Additive. Nothing the frozen web calls changes shape. `Kairos-Contract` is now `2026-11-05`. Schemas are in `shared/src/schemas.ts` (`forwardingStatusSchema`, `forwardingConfirmSchema`, `FORWARDING_STATES`).

## New routes (session)

**`GET /api/forwarding/status`** answers `{ state, address, lastMailAt, verification }`.

- `state` is one of `not_started`, `awaiting_verification`, `verified_pending_first_mail`, `active`, `stale`. It is informational: show the next step, and gate nothing on it.
- `verification` is `{ provider: "gmail", code, confirmUrl, expiresAt }` or `null`. Either `code` or `confirmUrl` can be null, but not both. It disappears after 3 days, or when the first real mail arrives.
- `confirmUrl` only ever points at Google's confirmation host, and the server has checked the mail's DKIM signature. Render it as a link that opens a new tab with `rel="noopener noreferrer"`.
- 404 `not_found` means the user has no profile yet.

**`POST /api/forwarding/confirm`** with `{ provider: "gmail" | "outlook" | "other" }` answers `{ state }`. This is the "I have set it up" button, the only signal Gmail or Outlook gives. It is idempotent, and it never moves an active connection back. A bad provider is 422 `invalid_body`.

`web/components/dashboard/settings/forwarding-address.tsx` still says "Confirm it with the code Gmail sends". Until now that code reached the user by accident, as an ordinary inbox row. It no longer appears there, so **this panel must ship with or before the new route going live**, or Gmail users only get the code by email.

## `GET /api/inbox`

- New optional filter: `?applicationId=<uuid>`. A bad value is 400 `invalid_param`.
- Gmail confirmations and hidden spam no longer appear.
- `preview` is at most 280 characters with whitespace collapsed, and `""` once the body passes 180 days. Treat it as plain text, since it is a stranger's words.
- The other fields are unchanged. `nextCursor` was already there.

## Notifications now produced

- `reply_important`: a linked interview, assessment or offer reply, with `detail: { applicationId, kind }`. The list joins `applicationId` and the job title.
- `forwarding_code`: a Gmail code arrived. Send the user to the panel; the row itself holds no code.

## Application stage

`applications.stage` now moves with replies, forward only, and `rejected` is final. A rejection or offer moves it only when the mail's sender is authenticated, so the inbox can show `kind: "rejection"` on an application whose stage has not moved: treat the tag as "the mail says" and the stage as "we are sure". The `reply_*` event's payload holds `authenticated` and `stageHeld`. The stage is on `GET /api/applications/:id` (below).

## Undoing a stage set by mail

**`POST /api/applications/:id/stage/clear`** (session, no body) answers `{ stage, detached }`. Show it wherever the stage shows, labelled for what it does, for example "This wasn't about my application".

- `stage` is what the application now holds: `"applied"` for a submitted application, `null` otherwise.
- The replies of the kind that set the old stage are detached. They stay in the inbox with `applicationId: null`, tag unchanged, and `detached` counts them.
- With no stage, or `applied`, there is nothing to undo: the answer is the current stage with `detached: 0`.
- Another user's id, or a missing one, is 404 `not_found`; a malformed id is 400 `invalid_param`.
- 409 `conflict` means a reply moved the stage at that moment. Re-read and let the user decide again.
- A later genuine reply can move the stage forward again.

`GET /api/applications/:id` now returns `stage` beside `application`, additive and nullable. There is no web UI for this yet.

## Users who forward by hand

A manual forward comes from the user's own address, so it never carries the employer's signature. It is stored, shown and tagged, and a rejection or offer in it never moves the stage. Tell these users in the forwarding panel and on the application: the stage is theirs to set. The place to set it is the tracker (WP-21), which does not exist yet; until then say that automatic forwarding is what moves the stage. An automatic Gmail forward keeps the original signature.

## Not built here

`GET /api/applications/:id/events` (messaging-26) is WP-21's. Reply events are written with the kinds `reply_confirmation`, `reply_rejection`, `reply_interview`, `reply_assessment` and `reply_offer`, and an undo as `stage_changed` with `undone: true`. Until WP-21 ships them, the web has no timeline to read.
