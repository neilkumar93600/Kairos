# WP-29 frontend hand-off

Nothing here breaks the frozen web or extension. Every change is additive.

## Extension (next release, not the frozen build)

**Claim before you fill.** This is what makes "two tabs cannot send the same item" true on the client.

- `POST /api/extension/claim` `{ applicationId }`. 200 `{ claimed: true, leaseExpiresAt }`: this tab may send, and has 10 minutes. 409 `already_claimed` `{ leaseExpiresAt }`: someone else holds it, **including another tab of this session**, so do not fill. 409 `conflict` `{ status }`: it is no longer approved.
- If the fill stops before the submit click, `POST /api/extension/release` `{ applicationId }`, 200 `{ released: boolean }`. If the claim's response was lost, release and claim again.
- An explicit claim that gets no report in 10 minutes fails as `no_report`: the user is told to check their email before resending.
- Retry `POST /api/extension/report` with the same body on a 429, 503 or network error. It is safe: a second `submitted` never charges twice. The frozen extension never retries, so a lost report is its largest remaining gap.

`GET /api/extension/queue` now takes a 10-minute lease per session, so an item another session holds is not listed. The six item keys have not changed.

## Web

- `POST /api/applications/approve` may answer `{ approved, skipped: [{ id, reason }] }`, with `skipped` absent when empty. Reasons today: `not_ready`, `facts_changed`, `company_cap`, `paused`, `posting_closed`. Show them on the row; the frozen web ignores the key.
- `POST /api/applications/:id/resend` `{ channel?: "extension" | "cloud", acknowledgeUnconfirmed?: boolean }` gives 200 `{ applicationId, status: "approved", attemptNo }`. Refusals: 409 `acknowledgement_required` `{ failureCode }` (ask, then send with `acknowledgeUnconfirmed: true`), 409 `not_approvable` `{ reason }`, 409 `conflict` `{ status }`, 402 `payment_required`. It is session-fresh like approve.
- `POST /api/matches/:id/queue` may answer 200 `{ applicationId: null, reason, existingApplicationId? }` with reason `already_queued`, `company_cap` or `too_many_pending`, and 409 `conflict` "This posting has closed".
- `POST /api/applications/:id/withdraw` may answer 409 `conflict` while the extension holds a lease, with a message that says how long. It now also takes a `failed` row.
- `PATCH /api/applications/:id` accepts `answers` on a failed row whose code is `required_missing`, so the user can fix them and resend. Other fields stay draft-only.
- A cloud send now shows `submitting` for up to 30 seconds after the run ends, until the worker's sweep settles it. Poll as you do today.
- `receipt` may hold `clientSubmittedAt`. `applications.failure_reason` gains the sentences for `timeout`, `no_report`, `cloud_unavailable_for_ats`, `extension_reported` and `render_failed`.
